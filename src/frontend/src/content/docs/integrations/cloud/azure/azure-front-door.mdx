[Azure Front Door](https://learn.microsoft.com/azure/frontdoor/) is a global, scalable entry point that uses Microsoft's edge network to deliver fast, secure, and highly available web applications. The Aspire Azure Front Door hosting integration provisions a Front Door profile and routes traffic to your backends.

## Hosting integration

The Aspire Azure Front Door hosting integration models the resource as the following type:

- `AzureFrontDoorResource`: Represents an Azure Front Door profile, including its endpoints, origin groups, origins, and routes.

To access this type and APIs, add the [📦 Aspire.Hosting.Azure.FrontDoor](https://www.nuget.org/packages/Aspire.Hosting.Azure.FrontDoor) NuGet package to your AppHost project.

<InstallPackage packageName="Aspire.Hosting.Azure.FrontDoor" />

### Add an Azure Front Door resource

In your AppHost, call <ApiReference name="Aspire.Hosting.AzureFrontDoorExtensions.AddAzureFrontDoor" /> to add a Front Door profile, then call <ApiReference name="Aspire.Hosting.AzureFrontDoorExtensions.WithOrigin" /> to attach a backend resource as an origin:

<Tabs syncKey="aspire-lang">
<TabItem id="csharp" label="C#">

```csharp title="AppHost.cs"
var builder = DistributedApplication.CreateBuilder(args);

builder.AddAzureAppServiceEnvironment("production");

var api = builder.AddProject<Projects.Api>("api")
    .WithExternalHttpEndpoints();

builder.AddAzureFrontDoor("frontdoor")
    .WithOrigin(api);

// After adding all resources, run the app...
builder.Build().Run();
```

</TabItem>
<TabItem id="typescript" label="TypeScript">

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

await builder.addAzureAppServiceEnvironment("production");

const api = await builder.addProject("api", "../Api/Api.csproj");
await api.withExternalHttpEndpoints();

const frontdoor = await builder.addAzureFrontDoor("frontdoor");
await frontdoor.withOrigin(api);

// After adding all resources, run the app...
await builder.build().run();
```

</TabItem>
</Tabs>

The preceding code:

- Adds an Azure App Service environment (a compute environment is required so Front Door can resolve the origin's hostname).
- Adds an `api` project and exposes it externally with <ApiReference name="Aspire.Hosting.ResourceBuilderExtensions.WithExternalHttpEndpoints" />. Front Door requires an origin to expose an external HTTP or HTTPS endpoint.
- Adds a Front Door profile named `frontdoor` and configures the `api` project as an origin.

Each call to `withOrigin` creates a separate Front Door endpoint, origin group, origin, and route, so each backend is independently routable through its own `*.azurefd.net` hostname.

<Aside type="caution">
  When you call `addAzureFrontDoor`, it implicitly calls
  <ApiReference name="Aspire.Hosting.AzureProvisionerExtensions.AddAzureProvisioning" />—which adds support for generating Azure resources
  dynamically during app startup. The app must configure the appropriate
  subscription and location. For more information, see [Local provisioning:
  Configuration](/integrations/cloud/azure/local-provisioning/#configuration).
</Aside>

### Add multiple origins

You can add multiple backends to the same Front Door profile. Each origin gets its own Front Door endpoint and route:

<Tabs syncKey="aspire-lang">
<TabItem id="csharp" label="C#">

```csharp title="AppHost.cs"
var builder = DistributedApplication.CreateBuilder(args);

builder.AddAzureAppServiceEnvironment("production");

var api = builder.AddProject<Projects.Api>("api")
    .WithExternalHttpEndpoints();

var web = builder.AddProject<Projects.Web>("web")
    .WithExternalHttpEndpoints();

builder.AddAzureFrontDoor("frontdoor")
    .WithOrigin(api)
    .WithOrigin(web);

builder.Build().Run();
```

</TabItem>
<TabItem id="typescript" label="TypeScript">


Each origin must be added at most once per Front Door resource — adding the same resource twice throws `InvalidOperationException`.

### Health probes

Front Door uses health probes to determine which origins are healthy. By default, the Aspire integration probes the origin's external endpoint at path `/` over HTTPS. If you have configured an HTTP probe on the origin (for example with <ApiReference name="Aspire.Hosting.ResourceBuilderExtensions.WithHttpProbe" />), Front Door uses the path and protocol from the resource's liveness probe instead.

### Provisioning-generated Bicep

When you publish your app, Aspire generates Bicep alongside the manifest. A Front Door resource with a single origin generates Bicep similar to the following:

<Aside type="caution">
  **Upgrading from Aspire 13.3.0-preview:** The resource names generated for Front Door profiles, endpoints, origin groups, origins, and routes changed in Aspire 13.4. This can result in duplicate Azure resources (profiles, endpoints, origin groups, routes, and origins) during an upgrade. To avoid duplicates, either remove the existing Azure resources before redeploying, or set resource names explicitly using <ApiReference name="Aspire.Hosting.AzureProvisioningResourceExtensions.ConfigureInfrastructure" />.
</Aside>

<Aside type="caution">
  **Upgrading from Aspire 13.5 or earlier:** Origin names changed in Aspire 13.6 to include the origin's backend hostname in addition to the resource group ID, so switching an origin's backend produces a new origin name instead of reusing the previous origin's identity. This changes the generated origin name even when the backend hostname hasn't changed, and can result in old and new origins coexisting in the same origin group after an upgrade (incremental ARM deployments don't remove resources omitted from the new template). The recommended approach is to adopt the new naming policy and manually delete the old origins after deploying and confirming that the new origins are healthy and serve the intended backends. If this isn't feasible, preserve the previous default origin names with `ConfigureInfrastructure` before the first deployment after upgrading. For more information, see [Breaking changes in Aspire 13.6](/whats-new/aspire-13-6/#front-door-origin-names-now-include-the-backend-hostname).
</Aside>

```bicep title="Generated Bicep — frontdoor.bicep"
@description('The location for the resource(s) to be deployed.')
param location string = resourceGroup().location

param my_api_host string

resource frontdoor 'Microsoft.Cdn/profiles@2025-06-01' = {
  name: take('frontdoor-${uniqueString(resourceGroup().id)}', 260)
  location: 'Global'
  sku: {
    name: 'Standard_AzureFrontDoor'
  }
  tags: {
    'aspire-resource-name': 'frontdoor'
  }
}

resource my_apiEndpoint 'Microsoft.Cdn/profiles/afdEndpoints@2025-06-01' = {
  name: take('myapiEndpoint-${uniqueString(resourceGroup().id)}', 46)
  location: 'Global'
  parent: frontdoor
}

resource my_apiOriginGroup 'Microsoft.Cdn/profiles/originGroups@2025-06-01' = {
  name: take('myapiOriginGroup-${uniqueString(resourceGroup().id)}', 90)
  properties: {
    healthProbeSettings: {
      probePath: '/'
      probeProtocol: 'Https'
    }
    loadBalancingSettings: {
      sampleSize: 4
      successfulSamplesRequired: 3
      additionalLatencyInMilliseconds: 50
    }
  }
  parent: frontdoor
}

resource my_apiOrigin 'Microsoft.Cdn/profiles/originGroups/origins@2025-06-01' = {
  name: take('myapiOrigin-${uniqueString(resourceGroup().id, my_api_host)}', 90)
  properties: {
    hostName: my_api_host
    originHostHeader: my_api_host
  }
  parent: my_apiOriginGroup
}

resource my_apiRoute 'Microsoft.Cdn/profiles/afdEndpoints/routes@2025-06-01' = {
  name: take('myapiRoute-${uniqueString(resourceGroup().id)}', 90)
  properties: {
    forwardingProtocol: 'HttpsOnly'
    httpsRedirect: 'Enabled'
    linkToDefaultDomain: 'Enabled'
    originGroup: {
      id: my_apiOriginGroup.id
    }
    patternsToMatch: [
      '/*'
    ]
  }
  parent: my_apiEndpoint
  dependsOn: [
    my_apiOrigin
  ]
}

output my_api_endpointUrl string = 'https://${my_apiEndpoint.properties.hostName}'
```

Aspire passes the origin's hostname (resolved from the compute environment, not the full URL) into the `my_api_host` parameter so the Front Door origin points at the deployed backend.

The generated Bicep is a starting point and is influenced by changes to the provisioning infrastructure in C#. Customizations to the Bicep file directly are overwritten, so make changes through the provisioning APIs to ensure they're reflected in the generated files.

#### Customize provisioning infrastructure

For advanced scenarios such as upgrading to the Premium SKU, attaching a Web Application Firewall (WAF) policy, configuring caching, or tuning routes, use `ConfigureInfrastructure` (`configureInfrastructure` in TypeScript) to modify the generated Bicep model directly:

<Tabs syncKey="aspire-lang">
<TabItem id="csharp" label="C#">

```csharp title="AppHost.cs"
using Azure.Provisioning.Cdn;

var frontDoor = builder.AddAzureFrontDoor("frontdoor")
    .WithOrigin(api)
    .ConfigureInfrastructure(infra =>
    {
        var resources = infra.GetProvisionableResources();

        // Upgrade to Premium SKU (required for WAF).
        var profile = resources.OfType<CdnProfile>().Single();
        profile.SkuName = CdnSkuName.PremiumAzureFrontDoor;

        // Enable caching on the route.
        var route = resources.OfType<FrontDoorRoute>().Single();
        route.CacheConfiguration = new FrontDoorRouteCacheConfiguration
        {
            QueryStringCachingBehavior = FrontDoorQueryStringCachingBehavior.IgnoreQueryString
        };
    });
```

</TabItem>
<TabItem id="typescript" label="TypeScript">

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

await builder.addAzureAppServiceEnvironment("production");

const api = await builder.addProject("api", "../Api/Api.csproj");
await api.withExternalHttpEndpoints();

const frontdoor = await builder.addAzureFrontDoor("frontdoor");
await frontdoor.withOrigin(api);
await frontdoor.configureInfrastructure(async (infra) => {
    // Use the AzureResourceInfrastructure API to customize Bicep
    // parameters or resources directly.
    await infra.addParameter("skuName", "Premium_AzureFrontDoor");
});

await builder.build().run();
```

</TabItem>
</Tabs>

Aspire selects the Premium SKU automatically when an origin uses [Private Link](#private-link-origins).

For more information, see [Customize Azure resources](/integrations/cloud/azure/customize-resources/). For the full list of configurable properties, see the [Azure.Provisioning.Cdn](https://learn.microsoft.com/dotnet/api/azure.provisioning.cdn) and [Azure.Provisioning.FrontDoor](https://learn.microsoft.com/dotnet/api/azure.provisioning.frontdoor) API documentation.

## Private Link origins

By default, Front Door reaches each origin over the public internet. With Azure Private Link, Front Door connects to Azure Container Apps or Azure App Service origins through a private endpoint. Aspire also disables public network access on those apps, so they're reachable only through Front Door.

Call `WithAzureFrontDoorPrivateLink` (`withAzureFrontDoorPrivateLink` in TypeScript) on the compute environment and pass the Front Door. Add apps with `WithOrigin` before or after this call. Only origins in the connected environment use Private Link, so one Front Door can serve both private and public origins. The call has no effect when you run the AppHost locally.

:::caution[Experimental]
`WithAzureFrontDoorPrivateLink` is experimental and might change in a future release. In C#, it reports the `ASPIREAZURE003` diagnostic as an error until you suppress it, for example with `#pragma warning disable ASPIREAZURE003`. For more information, see [ASPIREAZURE003](/diagnostics/aspireazure003/).
:::

### Requirements

- The AppHost references [📦 Aspire.Hosting.Azure.FrontDoor](https://www.nuget.org/packages/Aspire.Hosting.Azure.FrontDoor) and either [📦 Aspire.Hosting.Azure.AppContainers](https://www.nuget.org/packages/Aspire.Hosting.Azure.AppContainers) or [📦 Aspire.Hosting.Azure.AppService](https://www.nuget.org/packages/Aspire.Hosting.Azure.AppService). The examples also use `AddDotnetProject` from [📦 Aspire.Hosting.Dotnet](https://www.nuget.org/packages/Aspire.Hosting.Dotnet).
- Front Door uses the Premium tier, which Aspire selects automatically. For pricing, see the [Front Door tier comparison](https://learn.microsoft.com/azure/frontdoor/standard-premium/tier-comparison).
- The Container Apps environment is one that Aspire provisions, which is the default. Existing environments and Express environments aren't supported.
- The App Service plan uses a tier that supports [private endpoints](https://learn.microsoft.com/azure/app-service/overview-private-endpoint), such as Basic, Standard, or Premium. The default plan, `P0V3`, qualifies.

### Azure Container Apps

The following AppHost makes both apps private origins:

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

const environment = await builder.addAzureContainerAppEnvironment("env");
const frontDoor = await builder.addAzureFrontDoor("frontdoor");
await environment.withAzureFrontDoorPrivateLink(frontDoor);

const api = await builder.addDotnetProject("api", "../Api/Api.csproj")
    .withExternalHttpEndpoints();
const web = await builder.addDotnetProject("web", "../Web/Web.csproj")
    .withExternalHttpEndpoints()
    .withReference(api);

await frontDoor.withOrigin(api).withOrigin(web);

await builder.build().run();
```

</TabItem>

Aspire disables public network access on the Container Apps environment. Apps in the environment still reach each other directly, because [calls between apps in an environment](https://learn.microsoft.com/azure/container-apps/connect-apps) stay inside the environment. Callers outside the environment must use the Front Door endpoint.

For App Service:

- Each website gets its own private endpoint connection.
- Public network access is disabled on every app website in the environment, including websites that aren't Front Door origins.
- The Aspire dashboard is a separate website that stays public. If you don't need it, turn it off with `WithDashboard(false)` (`withDashboard({ enable: false })` in TypeScript).
- [Existing App Service plans](/integrations/cloud/azure/azure-app-service/azure-app-service-host/#connect-to-an-existing-app-service-plan) are supported.

If you deploy the `aspire publish` output yourself, deploy the environment and website modules before the Front Door module, and pass each website's resource ID and location to _main.bicep_.

#### Deployment slots

Front Door Private Link can't target a [deployment slot](/integrations/cloud/azure/azure-app-service/azure-app-service-host/#deployment-slots), so with `WithDeploymentSlot` each origin targets the production site. The slot has public network access disabled and isn't reachable through Front Door, so deploy to the slot and swap it into production.

With a deployment slot, Aspire doesn't update a production site that already exists. If that site is public, disable its public network access yourself.

#### Calls between apps

App Service has no internal route between apps. `WithReference` still resolves to each website's host name, which isn't publicly reachable. Callers must use the Front Door endpoint URLs or private networking and DNS that you set up. Don't pass a Front Door output to one of its own origins, because that creates a deployment dependency cycle. Configure those URLs after deployment instead.

### Approve the connection requests

Front Door creates each connection request in the `Pending` state. No traffic reaches the apps until you approve the requests, and Aspire doesn't approve them for you. Each request's description is `Azure Front Door <front-door> requests access to <environment>.` Front Door can create more than one request, so approve each one.

Approve the requests in the Azure portal, under **Networking** for the Container Apps environment or for each App Service website, or with the Azure CLI:

<Tabs syncKey='afd-private-link-target'>
<TabItem label='Container Apps'>

```bash title="Azure CLI"
az containerapp env list --resource-group <resource-group> --query "[].name" --output tsv
az network private-endpoint-connection list --type Microsoft.App/managedEnvironments --name <environment-name> --resource-group <resource-group> --query "[?properties.privateLinkServiceConnectionState.status=='Pending'].id" --output tsv
az network private-endpoint-connection approve --id <connection-id>
```

</TabItem>
<TabItem label='App Service'>

```bash title="Azure CLI"
az webapp list --resource-group <resource-group> --query "[].name" --output tsv
az network private-endpoint-connection list --type Microsoft.Web/sites --name <website-name> --resource-group <resource-group> --query "[?properties.privateLinkServiceConnectionState.status=='Pending'].id" --output tsv
az network private-endpoint-connection approve --id <connection-id>
```

Repeat the last two commands for each website.

</TabItem>
</Tabs>

Traffic starts flowing a few minutes after approval. Reach each app through its Front Door endpoint host name, which is listed on the Front Door profile's **Overview** page in the Azure portal. Requests to the app's own URL are denied.

### Private endpoint region

Front Door Private Link is available only in [some regions](https://learn.microsoft.com/azure/frontdoor/private-link#region-availability). Aspire creates the private endpoint in the region of the Container Apps environment or App Service website when that region is supported. Otherwise, it uses the supported region in the same Azure geography, such as `westus2` for `westus`, which adds a network hop but keeps data in the same geography. If the geography has no supported region, such as Switzerland, deployment fails.

To choose the region yourself, set it on each Private Link origin with `ConfigureInfrastructure` (`configureInfrastructure` in TypeScript). The following example works for both Container Apps and App Service:

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

In a TypeScript AppHost, first add the experimental [typed provisioning proxies](/integrations/cloud/azure/customize-resources/#enable-typed-provisioning-proxies) for Front Door:

```bash title="Aspire CLI"
aspire add Aspire.Hosting.Azure.Provisioning.Cdn
```

```typescript title="apphost.mts"
import { createBuilder, BicepValueKind } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

const environment = await builder.addAzureContainerAppEnvironment("env");
const frontDoor = await builder.addAzureFrontDoor("frontdoor");
await frontDoor.configureInfrastructure(async (infrastructure) => {
    for (const origin of await infrastructure.getFrontDoorOrigins()) {
        const privateLink = await origin.sharedPrivateLinkResource.get();
        const privateLinkId = await privateLink.privateLinkId.get();
        // Skip origins that don't use Private Link.
        if (await privateLinkId.kind() !== BicepValueKind.Unset) {
            await privateLink.privateLinkLocation.set("westus2");
        }
    }
});
await environment.withAzureFrontDoorPrivateLink(frontDoor);

const api = await builder.addDotnetProject("api", "../Api/Api.csproj")
    .withExternalHttpEndpoints();

await frontDoor.withOrigin(api);

await builder.build().run();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
#pragma warning disable ASPIREAZURE003 // WithAzureFrontDoorPrivateLink is experimental.

using Azure.Provisioning.Cdn;

var builder = DistributedApplication.CreateBuilder(args);

var environment = builder.AddAzureContainerAppEnvironment("env");
var frontDoor = builder.AddAzureFrontDoor("frontdoor")
    .ConfigureInfrastructure(infrastructure =>
    {
        foreach (var origin in infrastructure.GetProvisionableResources().OfType<FrontDoorOrigin>())
        {
            // Skip origins that don't use Private Link.
            if (!origin.SharedPrivateLinkResource.PrivateLinkId.IsEmpty)
            {
                origin.SharedPrivateLinkResource.PrivateLinkLocation = "westus2";
            }
        }
    });
environment.WithAzureFrontDoorPrivateLink(frontDoor);

var api = builder.AddDotnetProject("api", "../Api/Api.csproj")
    .WithExternalHttpEndpoints();

frontDoor.WithOrigin(api);

builder.Build().Run();
```

</TabItem>
</Tabs>

Changing the region of an existing deployment creates a new connection request that you must approve.

### Troubleshooting

| Symptom | Resolution |
| ------- | ---------- |
| Publish fails for an existing or Express Container Apps environment. | Use an environment that Aspire provisions. |
| Publish fails because none of the Front Door's origins run in the connected environment. | Add an app from that environment with `WithOrigin`, or remove the `WithAzureFrontDoorPrivateLink` call. |
| Publish fails because an origin runs in an environment that's connected to a different Front Door. | Also call `WithAzureFrontDoorPrivateLink` on that environment with this Front Door. |
| Requests through Front Door fail after deployment. | Approve every pending connection request, then wait a few minutes. |
| With a deployment slot, an existing production site is still publicly reachable. | Disable public network access on the site yourself. |
