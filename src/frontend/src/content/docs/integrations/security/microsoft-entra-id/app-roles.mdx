Application roles appear in the `roles` claim of tokens that Microsoft Entra ID issues for your API, so the API can tell a caller that holds `Orders.Read` from one that doesn't. They're separate from delegated scopes, from consent, and from Azure role-based access control (RBAC) roles. For the scope-based model, see [Expose and call APIs](/integrations/security/microsoft-entra-id/expose-and-call-apis/).

Aspire declares roles on registrations that it creates, and it can assign a role to a managed identity when you publish. It doesn't assign roles to users, groups, or applications.

## Declare application roles

Use `WithAppRole` to declare a role on a registration that Aspire creates. Declaring a role doesn't assign it to anyone.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

const entraApi = await builder.addEntraIdApplication("entra-api")
    .withAppRole("User", "User", "Can use the API.")
    .withAppRole("Admin", "Administrator", "Can administer the API.", {
        allowedMemberTypes: ["User", "Application"],
    });

const apiService = await builder.addDotnetProject("apiservice", "../Api/Api.csproj");
await apiService.withReference(entraApi);

await builder.build().run();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
using Aspire.Hosting.Azure;

var builder = DistributedApplication.CreateBuilder(args);

var entraApi = builder.AddEntraIdApplication("entra-api")
    .WithAppRole(new EntraIdAppRole("User", "User", "Can use the API."))
    .WithAppRole(new EntraIdAppRole("Admin", "Administrator", "Can administer the API.",
        ["User", "Application"]));

builder.AddDotnetProject("apiservice", "../Api/Api.csproj")
    .WithReference(entraApi);

// After adding all resources, run the app...
builder.Build().Run();
```

</TabItem>
</Tabs>

In TypeScript, you pass the values of the role to `withAppRole` and the optional settings in an options object. In C#, you create an `EntraIdAppRole` and pass it to `WithAppRole`.

| Setting | Description |
|---------|-------------|
| `value` | The value in the `roles` claim, such as `Admin`. It must be unique for the application. |
| `displayName` | The name that the Microsoft Entra admin center shows. |
| `description` | The text that assignment and consent experiences show. |
| `allowedMemberTypes` | The kinds of principals that can hold the role, passed through to Microsoft Graph. Use `User` for users and groups and `Application` for applications and managed identities. The default is `User`. |
| `id` | An optional GUID for the role. When omitted, Aspire derives a stable ID from the registration's resource name and the role value. |
| `isEnabled` | Whether the role can be assigned. The default is `true`. |

A role value can have at most 120 characters, can't start with a period, and can contain only ASCII letters, digits, and the punctuation that [Microsoft Graph allows](https://learn.microsoft.com/graph/api/resources/approle). Aspire rejects spaces and quotation marks when you write the AppHost. Two roles on one registration can't share an ID.

Role IDs stay the same across deployments, and changing a role's value or ID creates a different role.

:::caution
`WithAppRole` throws for registrations that you add with `AddExistingEntraApplication`, because Aspire never modifies an existing registration. For more information, see [Existing registrations](/integrations/security/microsoft-entra-id/existing-registrations/).
:::

### Understand how deployments update roles

Whenever a registration declares at least one role, Aspire sends the complete `appRoles` collection, and Microsoft Graph replaces what's stored. Include every role that you want to keep, including roles that someone added outside the AppHost.

- A role that you leave out fails the deployment with `CannotDeleteOrUpdateEnabledEntitlement` if it's still enabled.
- A role that you leave out is deleted if it's already disabled.
- When a registration declares no roles, Aspire doesn't send `appRoles`, so roles that the AppHost never declared are left alone.

### Retire a role

Retire a role in two steps.

1. Remove the `PublishWithAppRoleAssignment` calls for the role, set `isEnabled` to `false`, and leave the role declared. Deploy.
2. Remove the role from the AppHost and deploy again, while other roles remain declared.

A disabled role can't be assigned to anyone new. Microsoft Entra ID [keeps issuing it in tokens for existing assignments](https://learn.microsoft.com/entra/identity-platform/howto-add-app-roles-in-apps#app-roles-ui), so disabling isn't access revocation. Remove the existing assignments separately. You can't remove the last declared role from the AppHost. Keep it declared with `isEnabled` set to `false`, or delete it in the Microsoft Entra admin center.

## Assign roles to managed identities

`PublishWithAppRoleAssignment` grants a user-assigned managed identity an application role on an API registration that Aspire creates. A caller then authenticates directly as its managed identity, so it needs no registration of its own and no federated credential.

The role must be declared, enabled, and allow `Application` members. Aspire validates the role names when you write the AppHost, but it records the assignment only when you publish. Assignments don't apply when you run locally.

You can pass the managed identity or the workload that uses it. The workload overload uses the workload's attached identity. If the workload has none, a supported Azure deployment environment creates one.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

await builder.addAzureContainerAppEnvironment("env");

const worker = await builder.addContainer("worker", "my-worker-image");

const entraApi = await builder.addEntraIdApplication("entra-api")
    .withApplicationIdUri({ applicationIdUri: "api://orders" })
    .withAllowWebApiToBeAuthorizedByACL()
    .withAppRole("Orders.Read", "Read orders", "Read orders.", {
        allowedMemberTypes: ["Application"],
    })
    .publishWithAppRoleAssignment(worker, ["Orders.Read"]);

const api = await builder.addContainer("api", "my-api-image");
await api.withReference(entraApi);

// The caller requests a token for the API's application ID URI.
await worker.withEnvironment("ORDERS_API_SCOPE", "api://orders/.default");

await builder.build().run();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
using Aspire.Hosting.Azure;

var builder = DistributedApplication.CreateBuilder(args);

builder.AddAzureContainerAppEnvironment("env");

var callerIdentity = builder.AddAzureUserAssignedIdentity("caller-identity");

var worker = builder.AddDotnetProject("worker", "../Worker/Worker.csproj")
    .WithAzureUserAssignedIdentity(callerIdentity)
    // The caller requests a token for the API's application ID URI.
    .WithEnvironment("ORDERS_API_SCOPE", "api://orders/.default");

var entraApi = builder.AddEntraIdApplication("entra-api")
    .WithApplicationIdUri("api://orders")
    .WithAllowWebApiToBeAuthorizedByACL()
    .WithAppRole(new EntraIdAppRole("Orders.Read", "Read orders", "Read orders.", ["Application"]))
    .PublishWithAppRoleAssignment(callerIdentity, "Orders.Read");

builder.AddDotnetProject("api", "../Api/Api.csproj")
    .WithReference(entraApi);

// Alternatively, pass the workload instead of the identity:
// entraApi.PublishWithAppRoleAssignment(worker, "Orders.Read");

// After adding all resources, run the app...
builder.Build().Run();
```

</TabItem>
</Tabs>

In C#, `PublishWithAppRoleAssignment` has an overload for the identity and an overload for the workload. In TypeScript, one `publishWithAppRoleAssignment` method accepts either.

The default application ID URI is `api://{clientId}`, and the client ID exists only after the deployment creates the registration. This example sets an explicit URI so that the caller's scope is known when you write the AppHost. For other ways to set the URI, see [Set the application ID URI](/integrations/security/microsoft-entra-id/expose-and-call-apis/#set-the-application-id-uri).

### Configure the caller and the API

Configure the two sides differently.

- Reference the API's registration from the API workload, not from the caller. The registration's settings identify the API, so the API validates tokens with them.
- Call `WithAllowWebApiToBeAuthorizedByACL` on the API's registration. It stops Microsoft.Identity.Web from requiring a `roles` or `scp` claim in the token, so a token that has no roles reaches your authorization policy instead of being rejected during authentication.
- Give the caller the API's URL and the application ID URI as separate settings. The caller requests a token for the application ID URI followed by `/.default`.

In the Azure Container Apps template that Aspire generates, a workload with a user-assigned identity gets the `AZURE_CLIENT_ID` environment variable, set to the identity's client ID. The caller uses it to request a token as that identity:

```csharp title="Worker.cs"
var identityClientId = builder.Configuration["AZURE_CLIENT_ID"]!;
var credential = new ManagedIdentityCredential(
    ManagedIdentityId.FromUserAssignedClientId(identityClientId));

AccessToken token = await credential.GetTokenAsync(
    new TokenRequestContext([builder.Configuration["ORDERS_API_SCOPE"]!]),
    cancellationToken);

// Send token.Token to the API as a bearer token.
```

The API validates the token with Microsoft.Identity.Web and requires the assigned role on protected routes. An identity without the assignment can receive a token, but the token has no `roles` claim, so the authorization policy rejects the request with a 403 response. Authentication alone doesn't grant access.

```csharp title="Program.cs"
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"));

builder.Services.Configure<JwtBearerOptions>(JwtBearerDefaults.AuthenticationScheme, options =>
{
    options.MapInboundClaims = false;
    options.TokenValidationParameters.RoleClaimType = "roles";
});

builder.Services.AddAuthorization(options =>
    options.AddPolicy("orders", policy => policy.RequireAuthenticatedUser().RequireRole("Orders.Read")));

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

app.MapGet("/orders", () => "orders").RequireAuthorization("orders");
```

### Grant the deployer the required permissions

Assigning a role is a Microsoft Graph operation, and Azure subscription roles such as Owner or Contributor don't cover it. The identity that deploys needs `AppRoleAssignment.ReadWrite.All` and `Application.Read.All`, or a higher permission that covers reads. Application permissions require administrator consent. A delegated deployment, which runs as a signed-in user, also needs a [supported Microsoft Entra directory role](https://learn.microsoft.com/graph/api/serviceprincipal-post-approleassignedto#permissions). The callers don't need these Graph permissions.

Aspire assigns the role to the identity's principal (object) ID, not to its client ID.

:::caution
Removing an assignment call, changing its target, or excluding a caller doesn't revoke an existing grant. Remove grants explicitly through Microsoft Graph or the Microsoft Entra admin center. Existing tokens stay valid until they expire, and managed identity token caches can delay when callers observe a change.
:::

For the full permissions matrix, see [Lifecycle and permissions](/integrations/security/microsoft-entra-id/lifecycle-and-permissions/).

## Limitations

- `PublishWithAppRoleAssignment` throws for existing registrations. Create the assignment in the Microsoft Entra admin center instead.
- Aspire can't assign roles to users, groups, or applications. That includes giving a client registration an app role that an API in your AppHost declares.
- Aspire can't delete the last declared role, because it sends no `appRoles` when none remain. Keep the last role declared with `isEnabled` set to `false`, or delete it in the Microsoft Entra admin center.
