import { Tabs, TabItem } from '@astrojs/starlight/components';

An app that acquires tokens for itself, or that redeems authorization codes, is a confidential client and needs a client credential. An API that only validates incoming tokens needs none. Each credential method appends an entry to the `ClientCredentials` array that workloads receive, such as `AzureAd__ClientCredentials__0__SourceType`. You can configure more than one credential to form a fallback chain.

Aspire never creates, stores, or rotates client secrets or certificates for you, with one exception: the [local developer certificate](#local-developer-certificate) that Aspire generates for registrations it creates. The other methods describe a secret or certificate that already exists. Managed identity federation is also different, because Aspire creates the federated credential that establishes trust, but no secret or certificate.

## Choose a credential

| Credential | Method | Registrations | Applies when |
| ---------- | ------ | ------------- | ------------ |
| Client secret | `WithClientSecret` | Created and existing | Running and publishing |
| Local developer certificate | `RunWithLocalDeveloperCertificateCredential` | Created | Running |
| Managed identity that Aspire trusts | `PublishWithFederatedManagedIdentityCredential` | Created | Publishing |
| Managed identity that you configured | `WithFederatedManagedIdentityCredential` | Created and existing | Running and publishing |
| Key Vault certificate | `WithCertificateFromKeyVault` | Created and existing | Running and publishing |
| Certificate store | `WithCertificateThumbprint`, `WithCertificateDistinguishedName` | Created and existing | Running and publishing |
| Certificate file or signed assertion file | `WithCertificateFromFile`, `WithSignedAssertionFile` in TypeScript, `WithCredential` in C# | Created and existing | Running and publishing |

## Client secret

`WithClientSecret` passes a secret parameter to the workload. The parameter must be created as a secret.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

const tenantId = await builder.addParameter("entra-tenant-id");
const webClientId = await builder.addParameter("entra-web-client-id");
const webSecret = await builder.addParameter("entra-web-secret", { secret: true });

const entraWeb = await builder.addExistingEntraApplication("entra-web", tenantId, webClientId);
await entraWeb.withClientSecret(webSecret);

await builder.build().run();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var builder = DistributedApplication.CreateBuilder(args);

var tenantId = builder.AddParameter("entra-tenant-id");
var webClientId = builder.AddParameter("entra-web-client-id");
var webSecret = builder.AddParameter("entra-web-secret", secret: true);

var entraWeb = builder.AddExistingEntraApplication("entra-web", tenantId, webClientId)
    .WithClientSecret(webSecret);

// After adding all resources, run the app...
builder.Build().Run();
```

</TabItem>
</Tabs>

## Local developer certificate

For registrations that Aspire creates, opt in to a short-lived local certificate instead of copying a client secret. Aspire creates the certificate, registers only its public key with Microsoft Entra ID, and passes the private key to referencing workloads. Aspire never provisions a private key into Entra.

Combine the method with [managed identity federation](#managed-identity-federation) so the app has a credential both locally and when deployed. The local method does nothing when you publish.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
const entraWeb = await builder.addEntraIdApplication("entra-web")
    .runWithLocalDeveloperCertificateCredential()
    .publishWithFederatedManagedIdentityCredential();

const web = await builder.addDotnetProject("web", "../Web/Web.csproj");
await web.withReference(entraWeb);
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var entraWeb = builder.AddEntraIdApplication("entra-web")
    .RunWithLocalDeveloperCertificateCredential()
    .PublishWithFederatedManagedIdentityCredential();

builder.AddDotnetProject("web", "../Web/Web.csproj")
    .WithReference(entraWeb);
```

</TabItem>
</Tabs>

:::caution[Use separate development and production registrations]
Give each developer a distinct `Azure:TenantResourceSuffix`, and use a different suffix or registration name for production. Registrations are tenant-scoped, so different resource groups don't isolate them. The local method doesn't revoke a public key that a registration previously trusted. Never use a production registration with this feature.
:::

### Certificate lifetime and renewal

Aspire creates a dedicated, self-signed RSA certificate that is valid for 48 hours for each Entra ID resource. On a later AppHost run, it reuses the certificate when more than 24 hours remain. Otherwise it generates a replacement and updates the registration's public key credentials.

Renewal happens at startup. There is no background renewal and no credential reload in running workloads, so restart your development sessions before the certificate expires.

### Where the certificate is stored

The passwordless PFX file, including its private key, is stored in the AppHost-specific Aspire store at `dev-certs/Entra/<resource-name>.pfx`. It isn't stored in the user's global HTTPS certificate directory. The store honors `Aspire:Store:Path` and `ASPIRE__STORE__PATH`, and Aspire restricts the directory and the PFX file to the current user.

Renewal overwrites the same PFX file and doesn't keep earlier private keys. Aspire doesn't install the certificate in an operating system store or trust it as an HTTPS certificate. If the local material is missing or incompatible, Aspire regenerates it. A failed Microsoft Graph update leaves the new PFX file available for a retry.

### How the registration is updated

Only the public certificate is embedded in the generated Bicep and sent to Entra through the Microsoft Graph Bicep extension. Aspire owns the registration's entire `keyCredentials` collection. Each deployment replaces it with the selected certificate and doesn't read or keep existing keys. Don't add independently managed certificate credentials to a development registration. Renewal removes the previous public key, so sessions that use the old certificate must restart.

Microsoft Graph assigns the certificate credential ID. Aspire doesn't set `keyId`, which avoids targeting an immutable credential when you redeploy.

The identity that provisions the registration needs the usual create and update permissions. For delegated access, `Application.ReadWrite.All` is sufficient. An application identity can use `Application.ReadWrite.OwnedBy` for registrations that it owns, subject to tenant policy and consent. Workloads don't need these permissions.

### What workloads receive

`WithReference` passes the private PFX file as a secret parameter with `SourceType` set to `Base64Encoded` and the file contents in `Base64EncodedValue`. Projects that use Microsoft.Identity.Web receive these variables:

- `AzureAd__ClientCredentials__{index}__SourceType`
- `AzureAd__ClientCredentials__{index}__Base64EncodedValue`

Other resources keep their uppercase snake-case naming. The workload needs no certificate path, store access, bind mount, or image-build secret.

:::caution
Base64 isn't encryption. These values are sensitive runtime environment values that the workload and sufficiently privileged local or container tooling can read. Don't log them. Local credentials and paths are excluded from published manifests and deployment artifacts.
:::

### Limitations

- Existing registrations stay under your control. The method throws for `AddExistingEntraApplication` and rejects conversion with `AsExistingApplication`.
- AppHost shutdown and Azure resource group deletion don't delete the local PFX file or the tenant-scoped registration. Delete the registration and its service principal separately, and remove the PFX file from the AppHost store to discard the local credential. A public key can remain on the registration until a later deployment replaces it.

## Managed identity federation

For deployed apps, use a federated identity credential so that no secret is stored. The registration trusts a user-assigned managed identity, and the workload authenticates as the registration by using that identity.

### Create the trust for a registration that Aspire creates

`PublishWithFederatedManagedIdentityCredential` makes the registration trust the managed identity of each workload that references it.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
const entraWeb = await builder.addEntraIdApplication("entra-web")
    .publishWithFederatedManagedIdentityCredential();

const web = await builder.addDotnetProject("web", "../Web/Web.csproj");
await web.withReference(entraWeb);
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var entraWeb = builder.AddEntraIdApplication("entra-web")
    .PublishWithFederatedManagedIdentityCredential();

builder.AddDotnetProject("web", "../Web/Web.csproj")
    .WithReference(entraWeb);
```

</TabItem>
</Tabs>

Referencing the registration makes the workload need a user-assigned managed identity when published, the same way that referencing an Azure resource does. The workload uses the identity it already has, for example from `WithAzureUserAssignedIdentity`. Otherwise the Azure environment creates one, which requires a compute environment that supports managed identities such as `AddAzureContainerAppEnvironment`.

For each trusted identity, Aspire adds a `Microsoft.Graph/applications/federatedIdentityCredentials` resource to the generated Bicep with these values:

- The issuer is the tenant's v2.0 endpoint.
- The subject is the identity's object ID, also called its principal ID.
- The audience is the token-exchange audience of the application's cloud. Azure public, US Government, and China clouds are supported, and other clouds fail with an error.

The workload receives the identity's client ID as `ManagedIdentityClientId`. Deployment order is identity, then registration, then workload.

Managed identities exist only in Azure, so this method has no effect when you run the AppHost. Use the local developer certificate or another credential for local development.

### Trust specific workloads or identities

Pass a compute resource or a user-assigned identity to limit the trust. A compute resource that you pass must also reference the registration, and only that resource receives the credential.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
// Trust one workload.
const entraWeb = await builder.addEntraIdApplication("entra-web");
const web = await builder.addDotnetProject("web", "../Web/Web.csproj");
await web.withReference(entraWeb);
await entraWeb.publishWithFederatedManagedIdentityCredential({ identity: web });

// Trust one explicit identity.
const identity = await builder.addAzureUserAssignedIdentity("web-identity");
const entraAdmin = await builder.addEntraIdApplication("entra-admin")
    .publishWithFederatedManagedIdentityCredential({ identity });

const admin = await builder.addDotnetProject("admin", "../Admin/Admin.csproj");
await admin.withAzureUserAssignedIdentity(identity);
await admin.withReference(entraAdmin);
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
// Trust one workload.
var entraWeb = builder.AddEntraIdApplication("entra-web");
var web = builder.AddDotnetProject("web", "../Web/Web.csproj")
    .WithReference(entraWeb);

entraWeb.PublishWithFederatedManagedIdentityCredential(web);

// Trust one explicit identity.
var identity = builder.AddAzureUserAssignedIdentity("web-identity");
var entraAdmin = builder.AddEntraIdApplication("entra-admin")
    .PublishWithFederatedManagedIdentityCredential(identity);

builder.AddDotnetProject("admin", "../Admin/Admin.csproj")
    .WithAzureUserAssignedIdentity(identity)
    .WithReference(entraAdmin);
```

</TabItem>
</Tabs>

With an explicit identity, every workload that references the registration must use that identity. A validation step runs after the `azure-prepare-resources` pipeline step and fails, naming the resource, when a trusted workload has no managed identity or doesn't use the identity that the registration trusts.

The federated credential only changes how the app authenticates as itself. Interactive user sign-in still needs a [redirect URI](/integrations/security/microsoft-entra-id/redirect-uris-and-sign-in/) registered on the registration. Derive it from the web app's endpoint with `WithRedirectUris`, which uses the compute environment's host when deployed and doesn't make the registration depend on the web app.

### Use a managed identity trust that you created

Aspire never modifies an existing registration, so `PublishWithFederatedManagedIdentityCredential` throws for `AddExistingEntraApplication`. Create the trust yourself, then call `WithFederatedManagedIdentityCredential` with the managed identity's client ID. This method only configures the app, and it applies when you run locally as well as when you publish.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
await entraWeb.withFederatedManagedIdentityCredential("00001111-aaaa-2222-bbbb-3333cccc4444");
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
entraWeb.WithFederatedManagedIdentityCredential("00001111-aaaa-2222-bbbb-3333cccc4444");
```

</TabItem>
</Tabs>

Add a federated credential to the registration with these values. Otherwise, token requests fail with `AADSTS700213`.

- Set the issuer to the tenant's v2.0 endpoint, which is `https://login.microsoftonline.com/<tenant-id>/v2.0` in the Azure public cloud.
- Set the subject to the identity's principal ID.
- Set the audience to the token exchange audience of the cloud, which is `api://AzureADTokenExchange` in the Azure public cloud.

Pass the identity's client ID, not its principal ID, to `WithFederatedManagedIdentityCredential`. In TypeScript, an options object also accepts `tokenExchangeUrl` and `tokenExchangeAuthority` for other clouds. For more information, see [Configure an application to trust a managed identity](https://learn.microsoft.com/entra/workload-id/workload-identity-federation-config-app-trust-managed-identity).

Federation authenticates as the app registration by using a managed identity assertion. It differs from acquiring a token directly as the managed identity, which the [application roles](/integrations/security/microsoft-entra-id/app-roles/) page covers. It also doesn't enable mTLS proof-of-possession.

## Certificate from Azure Key Vault

Reference a Key Vault that you model in the AppHost instead of hard-coding its URL. This requires the [Azure Key Vault hosting integration](/integrations/cloud/azure/azure-key-vault/azure-key-vault-host/).

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
const vault = await builder.addAzureKeyVault("vault");

const entraWeb = await builder.addExistingEntraApplication("entra-web", tenantId, webClientId)
    .withCertificateFromKeyVault(vault, "MyCert");

const web = await builder.addDotnetProject("web", "../Web/Web.csproj");
await web.withReference(entraWeb);
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var vault = builder.AddAzureKeyVault("vault");

var entraWeb = builder.AddExistingEntraApplication("entra-web", tenantId, webClientId)
    .WithCertificateFromKeyVault(vault, "MyCert");

builder.AddDotnetProject("web", "../Web/Web.csproj")
    .WithReference(entraWeb);
```

</TabItem>
</Tabs>

The vault URI remains a deferred resource reference. A local run resolves the vault output, or its emulator endpoint, and published configuration keeps the vault output reference.

The certificate must already exist in the vault with an exportable private key, and its public key must already be registered on the Entra ID application. This helper doesn't create the certificate or upload the public key. Microsoft.Identity.Web always retrieves the latest certificate version and has no setting to select a specific one.

### Role assignments for certificate access

Microsoft.Identity.Web reads the certificate with its private key, which the vault's default **Key Vault Secrets User** role doesn't allow. Aspire grants the **Key Vault Certificate User** role automatically:

- When you run the AppHost, Aspire adds the role to the vault's default roles, so it's granted to the developer identity. If you called `ClearDefaultRoleAssignments` on the vault before `WithCertificateFromKeyVault`, Aspire adds nothing and you must assign roles yourself.
- When you publish, Aspire attaches the role to every workload that references the Entra ID application, whether you add the credential before or after `WithReference`. The publish target must support role assignments, such as `AddAzureContainerAppEnvironment`. Otherwise publishing fails with a "does not support role assignments" error.

To manage access yourself, call `WithRoleAssignments` on a workload for the vault before you reference the Entra ID application. Explicit assignments for that vault replace the automatic ones, and an empty role list grants none. For more information, see [Azure role assignments](/integrations/cloud/azure/role-assignments/).

You can model an existing vault with `RunAsExisting` or `PublishAsExisting`. Its access policies or RBAC configuration must allow certificate retrieval.

### Use a vault URL

When the vault is managed outside the AppHost, pass its URL instead. In this case, configure access and identity yourself.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"

```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"

```

## Certificate from the certificate store

Use a thumbprint or a distinguished name to locate a certificate in the store on the machine that runs the workload.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
await entraWeb.withCertificateThumbprint("CurrentUser/My", "ABC123...");

// Or locate the certificate by subject.
await entraWeb.withCertificateDistinguishedName("CurrentUser/My", "CN=MyCert");
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
entraWeb.WithCertificateThumbprint("CurrentUser/My", "ABC123...");

// Or locate the certificate by subject.
entraWeb.WithCertificateDistinguishedName("CurrentUser/My", "CN=MyCert");
```

</TabItem>

## Certificate file or signed assertion file

The file paths identify files on the consumer, not files that the AppHost reads. A certificate password must be a secret parameter. File credentials aren't recommended for production.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
const certificatePassword = await builder.addParameter("certificate-password", { secret: true });

await entraWeb.withCertificateFromFile("/certs/client.pfx", { password: certificatePassword });
await entraWeb.withSignedAssertionFile({ filePath: "/tokens/assertion" });
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
using Aspire.Hosting.Azure;

var certificatePassword = builder.AddParameter("certificate-password", secret: true);

entraWeb
    .WithCredential(new EntraIdFileCertificateCredential
    {
        FilePath = "/certs/client.pfx",
        Password = certificatePassword.Resource
    })
    .WithCredential(new EntraIdSignedAssertionFileCredential { FilePath = "/tokens/assertion" });
```

</TabItem>
</Tabs>

Omit the file path of a signed assertion file to use the consumer's `AZURE_FEDERATED_TOKEN_FILE` setting. C# AppHosts use `WithCredential` for credential types that don't have a dedicated method. TypeScript and other polyglot AppHosts use the typed methods instead.

## Send the certificate chain

`WithSendX5C` sends the `x5c` claim, which carries the public certificate, with token requests. This enables certificate rollover without redeploying the app. It applies only to certificate-based credentials and increases the size of each token request, so it's opt-in.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
await entraWeb.withSendX5C();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
entraWeb.WithSendX5C();
```

</TabItem>
</Tabs>
