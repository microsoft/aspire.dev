Aspire's AppHost is the code-first place where you declare the resources in your distributed application and the relationships between them. Aspire evaluates that model to orchestrate local development, populate the dashboard, and provide inputs to publishing and deployment workflows.

## AppHost language and workload language

The language of the AppHost controls how you write the application model. It doesn't restrict the languages used by the services that the AppHost orchestrates. A TypeScript AppHost can run a C# API, a Python worker, and a JavaScript frontend; a Python or Go AppHost can describe the same resources when the required APIs are generated.

AppHost authoring is currently established for **TypeScript** and **C#**. **Python**, **Go**, **Java**, and **Rust** AppHosts are experimental and hidden behind individual feature flags.

## Define resources and relationships

The following examples create the same application model: a Redis resource named `cache`.

const builder = await createBuilder();

const cache = await builder.addRedis('cache');

await builder.build().run();

<Fragment slot="go">

```go title="apphost.go"
package main

import (
	"log"

	"apphost/modules/aspire"
)

func main() {
	builder, err := aspire.CreateBuilder()
	if err != nil {
		log.Fatal(aspire.FormatError(err))
	}

	cache := builder.AddRedis("cache")
	if err := cache.Err(); err != nil {
		log.Fatal(aspire.FormatError(err))
	}

	app, err := builder.Build()
	if err != nil {
		log.Fatal(aspire.FormatError(err))
	}
	if err := app.Run(); err != nil {
		log.Fatal(aspire.FormatError(err))
	}
}
```

</Fragment>

```java title="AppHost.java"

```

Each resource has a stable name. References such as `WithReference`, `withReference`, `with_reference`, and their generated equivalents pass connection information from one resource to another. Dependency APIs such as `WaitFor` delay startup until another resource reaches the required state.

:::note[Generated APIs]
TypeScript, Python, Go, Java, and Rust AppHosts use SDKs generated from the same ATS metadata on the .NET hosting integrations. The exact generated signature can differ by language because each SDK follows that language's naming, error, and fluent conventions.
:::

## How the AppHost runs

For a C# AppHost, the AppHost process hosts the application model directly. Guest-language AppHosts use a guest/host architecture:

1. The Aspire CLI restores the hosting integration packages from `aspire.config.json`.
1. The Aspire Type System scans exported APIs and generates the language SDK in `.aspire/modules`.
1. The CLI starts the .NET orchestration host and creates a local authenticated transport.
1. The guest AppHost runs in its language runtime and invokes the generated SDK.
1. The host starts resources, applies references and health checks, and updates the dashboard.

<LearnMore>
  For the transport, authentication, and code-generation details, see
  [Multi-language architecture](/architecture/multi-language-architecture/).
</LearnMore>

## AppHost lifecycle

An AppHost follows the same high-level lifecycle in every language:

1. **Create the builder** and load AppHost configuration.
1. **Add resources** such as projects, executables, containers, databases, and caches.
1. **Add relationships** such as references, endpoints, health checks, and startup dependencies.
1. **Build the model** so Aspire can validate the resource graph.
1. **Run, publish, or deploy** the model through the Aspire CLI.

The Aspire CLI is the supported entry point for guest-language AppHosts because it prepares the host process, generates the SDK, configures the local transport, and selects the language runtime.

## Project configuration

Guest-language AppHosts use `aspire.config.json` to record:

- `appHost.path`: the AppHost entry file.
- `appHost.language`: the CLI language ID (`typescript/nodejs`, `python`, `go`, `java`, or `rust`).
- `packages`: hosting integrations and versions used to generate the SDK.
- `profiles`: dashboard, OTLP, and resource-service endpoints.
- `features`: optional project-scoped feature flags.

Run `aspire add <integration>` to update the package set, and run `aspire restore` to regenerate `.aspire/modules` without starting the application.

<Aside type="caution" title="Generated directory">
  Don't edit `.aspire/modules`. Changes are replaced the next time Aspire
  restores or regenerates the AppHost SDK.
</Aside>

## Best practices

- Keep the AppHost focused on resources and relationships, not application business logic.
- Use stable resource names because they become service-discovery and configuration keys.
- Add integrations with `aspire add` so the CLI updates configuration and generated SDKs together.
- Check errors using the convention of your generated SDK: exceptions in Python and Java, returned or accumulated errors in Go, and `Result` in Rust.
- Commit AppHost source and `aspire.config.json`; regenerate `.aspire/modules` with `aspire restore`.
- Treat experimental language APIs as generated contracts that can still change.
