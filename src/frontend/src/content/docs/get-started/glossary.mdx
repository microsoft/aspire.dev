This glossary defines terms used throughout the Aspire documentation.

## Core concepts

### AppHost

The **AppHost** is the code-first entry point that declares resources and their relationships. Aspire uses the resulting model for local orchestration, dashboard views, publishing, and deployment workflows.

### AppHost language

The **AppHost language** is the language used to express the application model. It doesn't constrain the languages of the workloads in that model.

| Language   | CLI language ID     | Entry file                                          | Status       |
| ---------- | ------------------- | --------------------------------------------------- | ------------ |
| TypeScript | `typescript/nodejs` | `apphost.mts`                                       | Established  |
| C#         | `csharp`            | `apphost.cs`, `AppHost.cs`, or a C# AppHost project | Established  |
| Python     | `python`            | `apphost.py`                                        | Experimental |
| Go         | `go`                | `apphost.go`                                        | Experimental |
| Java       | `java`              | `AppHost.java`                                      | Experimental |
| Rust       | `rust`              | `apphost.rs`                                        | Experimental |

### Resource

A **resource** is an item in the application model. Examples include application projects, executables, containers, databases, caches, message brokers, cloud resources, parameters, and connection strings.

Every resource has a name. Aspire uses that name in dashboard views, service-discovery data, environment variables, connection strings, and deployment artifacts.

### Resource builder

A **resource builder** is the fluent object returned when the AppHost adds a resource. Methods on the builder configure annotations, endpoints, references, health checks, persistence, commands, and other resource behavior.

Guest-language resource builders are generated wrappers around host-side resource builders.

### Distributed application

A **distributed application** is a system made of multiple independently running resources that communicate over a network or shared infrastructure. Aspire models those resources as one application even when they use different languages, frameworks, and deployment targets.

### Application model

The **application model** is the graph produced by the AppHost. It contains resources, annotations, endpoints, references, and dependency relationships. The orchestration host validates and executes this graph.

### Guest-language AppHost

A **guest-language AppHost** runs outside the .NET orchestration host and communicates with it through a generated SDK. TypeScript, Python, Go, Java, and Rust use this architecture.

### Aspire Type System

The **Aspire Type System (ATS)** is the language-neutral contract used to export .NET hosting APIs into generated guest SDKs. ATS describes capabilities, handles, DTOs, callbacks, collections, unions, and documentation.

### Generated SDK

The **generated SDK** is the language-specific API emitted under `.aspire/modules` from ATS exports in the AppHost's hosting packages. Run `aspire restore` to regenerate it. Don't edit generated SDK files manually.

### Polyglot

In this documentation, **polyglot** describes AppHosts, workloads, generated SDKs, integrations, or tooling that span multiple programming languages.

## Relationships and dependencies

### Reference

A **reference** connects one resource to another. APIs such as `WithReference`, `withReference`, `with_reference`, and the generated language equivalent pass service-discovery or connection information to the consuming resource.

Connection-string references commonly become environment variables such as `ConnectionStrings__cache`.

### WaitFor

**WaitFor** adds a startup dependency. The consuming resource waits for the dependency to satisfy its health checks instead of merely waiting for the process to start.

Use **WaitForStart** when running is sufficient, and **WaitForCompletion** when the dependency must finish successfully before the consuming resource starts. Verify the exact generated method in `.aspire/modules` for experimental AppHost languages.

### Service discovery

**Service discovery** lets resources find one another by logical name instead of hardcoded host and port values. The AppHost generates endpoint configuration and passes it to referenced workloads.

### Connection string

A **connection string** is a formatted value required to connect to a database, cache, queue, or another resource. Aspire can generate it from a managed resource or read an existing value from AppHost configuration.

### Health check

A **health check** reports whether a resource is ready or alive. Aspire uses health checks in dashboard status, dependency ordering, and deployment workflows.

## Integrations and SDKs

### Hosting integration

A **hosting integration** is a package used by the AppHost to add and configure resource types. For example, `Aspire.Hosting.Redis` exports the Redis resource APIs.

For guest AppHosts, the integration must expose an ATS-compatible surface before its APIs can appear in the generated SDK.

### Client integration

A **client integration** configures application code to consume a resource. It can register clients, read connection strings, add telemetry, and add health checks inside a workload.

Hosting integrations belong in the AppHost. Client integrations belong in the application that consumes the resource.

### Capability

A **capability** is an ATS-exported operation that the host can invoke for a guest SDK. Runtime dispatch uses a stable capability ID rather than a C# overload signature.

### Handle

A **handle** is an opaque identifier for an object that remains in the host process. Guest SDK wrappers use handles for resources, builders, endpoint references, and other live host-side objects.

### DTO

A **data transfer object (DTO)** is a JSON-shaped value that crosses the guest/host boundary by value. ATS DTOs should contain portable scalar, collection, enum, union, or nested DTO values rather than service providers or other runtime-only objects.

## Execution and operations

### Run mode

**Run mode** starts the application locally. `aspire run` restores the AppHost, starts resources, configures service discovery, and provides the dashboard.

### Publish mode

**Publish mode** evaluates publishers against the application model and writes deployment artifacts without necessarily deploying them.

### Deploy mode

**Deploy mode** executes deployment steps for a configured target. Deployment support depends on the target package and the APIs available to the selected AppHost language.

### Aspire Dashboard

The **Aspire Dashboard** displays resources, endpoints, logs, traces, metrics, health, and commands for the running application.

### OpenTelemetry

**OpenTelemetry** is the standard Aspire uses for logs, traces, and metrics. Workloads configure their language-specific OpenTelemetry SDKs and export telemetry to the endpoint provided by Aspire.

### Service Defaults

**Service Defaults** is the C# project pattern that configures OpenTelemetry, health checks, service discovery, and HTTP resilience in .NET workloads. Other workload runtimes use their own OpenTelemetry and resilience libraries.

## Experimental feature flags

The experimental AppHost flags are:

- `experimentalPolyglot:python`
- `experimentalPolyglot:go`
- `experimentalPolyglot:java`
- `experimentalPolyglot:rust`

Set one globally with:

```bash title="Enable an experimental AppHost language"
aspire config set features:experimentalPolyglot:python true --global
```

You can also set the exact key to `true` in the `features` object of a project's `aspire.config.json`.
