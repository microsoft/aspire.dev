A C# [AppHost](/get-started/app-host/) is a standard .NET app that uses `Microsoft.NET.Sdk`. Two packages turn it into an AppHost:

- [📦 Aspire.Hosting.AppHost](https://www.nuget.org/packages/Aspire.Hosting.AppHost) supplies the AppHost APIs and build targets.
- [📦 Aspire.Hosting.Dotnet](https://www.nuget.org/packages/Aspire.Hosting.Dotnet) supplies `AddDotnetProject` for adding .NET projects and file-based apps as resources.

Add other hosting integrations, such as Redis or PostgreSQL, as additional packages.

<Tabs syncKey='sdk'>

<TabItem label='Project file'>

```xml title='MyApp.AppHost.csproj'
<Project Sdk="Microsoft.NET.Sdk">

    <PropertyGroup>
        <OutputType>Exe</OutputType>
        <TargetFramework>net10.0</TargetFramework>
        <!-- Omitted for brevity -->
    </PropertyGroup>

    <ItemGroup>
        <PackageReference Include="Aspire.Hosting.AppHost" Version="%ASPIRE_VERSION%" />
        <PackageReference Include="Aspire.Hosting.Dotnet" Version="%ASPIRE_VERSION%" />
    </ItemGroup>

</Project>
```

</TabItem>
<TabItem label="File-based app">

```csharp title='apphost.cs'
#:package Aspire.Hosting.AppHost@%ASPIRE_VERSION%
#:package Aspire.Hosting.Dotnet@%ASPIRE_VERSION%

var builder = DistributedApplication.CreateBuilder(args);

// Omitted for brevity
```

## Reference .NET projects

Add .NET projects to the AppHost with `AddDotnetProject` and the path to a project or file-based app. The AppHost doesn't need a `ProjectReference` to the services it runs, so building the AppHost doesn't build them. Keep the services in your solution and CI builds.

<LearnMore>
For more information, see [.NET hosting](/integrations/frameworks/dotnet/dotnet-host/).
</LearnMore>

### Generated project metadata

Legacy APIs such as `AddProject<TProject>` take a generated class from the `Projects` namespace instead of a path. The AppHost build generates a class for each `ProjectReference` marked with `IsAspireProjectResource="true"`. Set `ReferenceOutputAssembly="false"` so the AppHost doesn't compile against the service:

```xml title="MyApp.AppHost.csproj"
<ItemGroup>
  <ProjectReference Include="..\MyService\MyService.csproj"
                    IsAspireProjectResource="true"
                    ReferenceOutputAssembly="false" />
</ItemGroup>
```

The generated class name is based on the project name. To customize it, for example when two projects have the same name, set `AspireProjectMetadataTypeName`:

```xml title="MyApp.AppHost.csproj"
<ItemGroup>
  <ProjectReference Include="..\Microservice1\Presentation.Api\Presentation.Api.csproj"
                    IsAspireProjectResource="true"
                    ReferenceOutputAssembly="false"
                    AspireProjectMetadataTypeName="MicroService1" />
  <ProjectReference Include="..\Microservice2\Presentation.Api\Presentation.Api.csproj"
                    IsAspireProjectResource="true"
                    ReferenceOutputAssembly="false"
                    AspireProjectMetadataTypeName="MicroService2" />
</ItemGroup>
```

This generates `Projects.MicroService1` and `Projects.MicroService2`. A `ProjectReference` without `IsAspireProjectResource="true"` is an ordinary reference, such as a shared library.

## AppHost build features

### Orchestrator dependencies

The AppHost relies on the [Aspire Dashboard](/dashboard/overview/) and other orchestration dependencies, such as the developer control plane (DCP) packages. These dependencies are specific to the platform that the AppHost is built on.

When the AppHost project runs, the orchestrator relies on these dependencies to provide the necessary functionality to the AppHost. For more information, see [Aspire orchestration overview](/get-started/app-host/).

### Use the Aspire CLI bundle for orchestration dependencies

The AppHost build sources the binaries for these dependencies from the installed **Aspire CLI bundle**. Those binaries update when you update the Aspire CLI through [`aspire update --self`](/reference/cli/commands/aspire-update/).

C# AppHosts require the Aspire CLI bundle, so [install the Aspire CLI](/get-started/install-cli/) before you build or run them. If `AspireUseCliBundle` is set to `false`, whether in the project, in `Directory.Build.props`, or through an environment variable, the build fails with error [`ASPIRE013`](/diagnostics/aspire013/), which can't be suppressed. Remove that setting or set it to `true`. In Aspire versions before 17.0, `AspireUseCliBundle` defaults to `false` for all AppHosts, so set it to `true` to use the bundle.

With the CLI bundle:

- Your AppHost uses the DCP and Dashboard versions installed with the Aspire CLI.
- The AppHost build selects the executable used to launch the AppHost as follows:
  1. An explicit `AspireCliPath` is always authoritative.
  2. When `AspireCliInvocationMode` is set to `Dnx` or `DnxPinned`, the build selects a usable `dnx` host.
  3. Otherwise, the default `Path` mode selects a compatible `aspire` on `PATH`, then falls back to the Aspire CLI package paired with `Aspire.Hosting.AppHost` through DNX.
- `AspireCliBundlePath` isn't an executable candidate. It explicitly identifies a bundle layout for DCP and Dashboard resolution.
- If the resolved Aspire CLI has a bundle that hasn't been extracted yet, the build runs `aspire setup` through the selected `aspire` or paired DNX invocation to extract it, then resolves the bundle again. This lets an AppHost build and launch from an IDE even when the CLI installation didn't run the release install scripts.
- If a required bundle layout can't be resolved, the build emits error [`ASPIRE009`](/diagnostics/aspire009/). Invalid explicit `AspireCliPath` and `AspireCliBundlePath` values remain authoritative and can produce this error.
- If `Dnx` or `DnxPinned` mode can't find `dnx`, the run preflight emits error [`ASPIRE011`](/diagnostics/aspire011/) when it prepares the launch command. A regular build doesn't emit this diagnostic.

:::note[Advanced scenario: Override the bundle path]
Most apps don't need to set either path. `AspireCliPath` selects an explicit `aspire` executable for invocation and bundle discovery. `AspireCliBundlePath` supplies an explicit unpacked bundle layout for DCP and Dashboard resolution, but it doesn't select the executable used to launch the AppHost:

```xml title="MyApp.AppHost.csproj"
<PropertyGroup>
  <!-- Select an explicit aspire executable: -->
  <AspireCliPath>/usr/local/bin/aspire</AspireCliPath>
  <!-- Or identify an explicit unpacked bundle layout: -->
  <!-- <AspireCliBundlePath>/path/to/aspire/bundle</AspireCliBundlePath> -->
</PropertyGroup>
```
:::

#### Running with aspire run or aspire start

When you start an AppHost with `aspire run` or `aspire start`, the CLI automatically passes the resolved bundle paths through the `ASPIRE_DCP_PATH` and `ASPIRE_DASHBOARD_PATH` environment variables.

#### Running with dotnet run

When you start the AppHost with `dotnet run` instead of `aspire run`, the AppHost resolves and invokes the Aspire CLI itself. Set `AspireCliInvocationMode` to control how that invocation happens:

- **`Path`** (default) — resolves a compatible `aspire` command from `AspireCliPath` (if set) or `PATH`. If no compatible command is found, it falls back to invoking the `Aspire.Cli` version paired with `Aspire.Hosting.AppHost` through [`dnx`](https://learn.microsoft.com/dotnet/core/tools/dotnet-tool-exec).
- **`Dnx`** — always invokes the Aspire CLI through `dnx`, using the unversioned `Aspire.Cli` package. This honors an in-scope [.NET local tool manifest](https://learn.microsoft.com/dotnet/core/tools/local-tools-how-to-use#create-a-manifest-file) (`.config/dotnet-tools.json`) if one pins `Aspire.Cli`, or resolves the latest published package when no manifest applies.
- **`DnxPinned`** — always invokes the Aspire CLI through `dnx`, using `Aspire.Cli@<version>` pinned to the exact `Aspire.Cli` version paired with `Aspire.Hosting.AppHost`. Use this when the CLI must match the AppHost package version exactly, ignoring any local tool manifest.

Set `AspireCliInvocationMode` in your AppHost `.csproj`:

```xml title="MyApp.AppHost.csproj"
<PropertyGroup>
  <AspireCliInvocationMode>Dnx</AspireCliInvocationMode>
</PropertyGroup>
```

:::note
`dotnet run` is noninteractive, so `dnx` restores and executes without prompting for confirmation and uses your configured NuGet sources. Restore or probe failures fail explicitly instead of falling back to an incomplete direct launch. If `dnx` can't be found on `PATH` when `Dnx` or `DnxPinned` mode is configured, the run preflight emits error `ASPIRE011` when it prepares the launch command. Install or use the .NET SDK 10.0 or later, set `AspireCliInvocationMode` to `Path` to use the global `aspire` command, or set `AspireCliPath` to an explicit Aspire CLI executable.
:::

`dotnet run` hands the AppHost to `aspire run`, so use it only to run the AppHost locally. To generate deployment artifacts, use [`aspire publish`](/reference/cli/commands/aspire-publish/) instead of `dotnet run --operation publish`. An AppHost started in publish mode this way fails with an error that points you to `aspire publish`. For more information, see [`dotnet run --operation publish` fails in publish mode](/get-started/troubleshooting/#dotnet-run---operation-publish-fails-in-publish-mode).
