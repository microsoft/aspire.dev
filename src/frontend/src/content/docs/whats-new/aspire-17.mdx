Aspire 17.0 puts your resources at the center of a **redesigned dashboard**, with a resource table home page, a dedicated **Terminals** page, and graph export to Mermaid. **Go AppHosts are generally available**, a **tray companion** keeps running AppHosts within reach, and the **Kubernetes deployment packages are stable**. Many APIs that previously required an experimental-warning suppression are now stable, too.

This release introduces:

- A redesigned dashboard with a resource table home page, a Terminals page, Mermaid export, and first-run telemetry guidance.
- A CLI that adds shell completion, environment-specific secrets, team template, integration, and skill sources, plus a preview tray companion.
- Generally available Go AppHosts with templates, debugging, `aspire doctor` checks, and SDK export.
- AppHost updates including optional parameters, browser-origin references, TypeScript Azure Functions, and graduated APIs.
- New Microsoft Entra ID and Azure API Management integrations.
- Stable Kubernetes deployment with Helm 4, AKS Standard tier and OS SKU selection, and cert-manager External Account Binding.
- Integration updates for Azure Web PubSub, Azure Service Bus, Redis output caching, and Deno.
- Updated default container images, including MongoDB `9.0`, PostgreSQL `18.6`, and Redis `8.10`.
- …and much more.

We'd love to hear what you think. Drop by [<Icon name="discord" class='d-inline' /> Discord](https://aka.ms/aspire-discord) to chat with the team and the community, or file feedback and issues on [<Icon name="github" class='d-inline' /> GitHub](https://github.com/microsoft/aspire/issues).

Keep the resources you're investigating in view as you move between logs, traces, and metrics. The redesigned dashboard adds a shared resource pane with search, filters, and multi-selection, plus grouping by tags, resource type, or state.

The new experience is still evolving. You can switch to the previous dashboard from **Settings** when the previous experience is available in your dashboard distribution.

## 🛠️ CLI updates

### Shell completion

Complete Aspire commands and options in Bash, Fish, PowerShell, and Zsh. Generate a completion script with `aspire completions script`, specifying `bash`, `fish`, `pwsh`, or `zsh` when you want to select the shell explicitly.

For example, generate and load a Bash completion script for your current shell session:

```bash title="Aspire CLI — Generate Bash completions"
aspire completions script bash > aspire-completion.bash
source ./aspire-completion.bash
```

For installation details, see [microsoft/aspire#20026](https://github.com/microsoft/aspire/pull/20026).

### Environment-specific secrets

Keep deployment secrets separate by using `--environment` or `-e` with the `aspire secret` commands.

Run the secret commands from your AppHost directory. You can set a secret without putting its value in the command line: omit the value to enter it at a masked interactive prompt, or use `--envvar` to read an environment variable:

```bash title="Aspire CLI — Set a deployment secret from an environment variable"
aspire secret set Parameters:database-password --environment production --envvar DATABASE_PASSWORD
```

Set `DATABASE_PASSWORD` in your environment before running this command. Non-interactive calls must supply a value or `--envvar`; they don't open an input prompt.

For details, see [microsoft/aspire#20135](https://github.com/microsoft/aspire/pull/20135) and [microsoft/aspire#20984](https://github.com/microsoft/aspire/pull/20984).

### Custom templates, integrations, and skills

Bring your team's project scaffolding, hosting packages, and agent guidance into the Aspire CLI. Named sources let you reuse these across apps without replacing Aspire's built-in choices. Use sources you trust: templates and agent plugins can contain executable code.

#### Custom templates

Try templates directly from a Git repository without registering a source. For example, browse the Azure-focused templates in [Azure/aspire-templates](https://github.com/Azure/aspire-templates):

```bash title="Aspire CLI — Try Azure templates"
aspire new --template-repository https://github.com/Azure/aspire-templates
```

Fork the repository and customize a template for your team. Push your changes to a branch, then use `--template-repository-ref` to test it before merging:

```bash title="Aspire CLI — Test a template branch"
aspire new --template-repository https://github.com/example-org/aspire-templates \
  --template-repository-ref custom-starter
```

Replace `example-org` with your fork's owner and `custom-starter` with your branch. The ref can also be a tag or full commit SHA; omitting it uses the repository's default branch. Use `--template-path` to select a directory within the repository.

When you want to reuse a source, add a persistent reference in your global Aspire settings:

```bash title="Aspire CLI — Save a template source"
aspire template source add azure --repository https://github.com/Azure/aspire-templates
aspire new
```

The CLI asks you to confirm that you trust the source before registering it. Use `--path` for a template directory within the repository and `--ref` to pin a branch, tag, or full commit SHA.

#### Custom integrations

Make your hosting integrations discoverable from a NuGet server. Add an `integrationSources` entry to `aspire.config.json`; optional package patterns limit which packages the source offers:

```json title="aspire.config.json — Discover team integrations"
{
  "integrationSources": {
    "team": {
      "source": "https://nuget.example.com/v3/index.json",
      "patterns": ["Team.Hosting.*"]
    }
  }
}
```

Replace the illustrative feed URL with your NuGet server's service index and publish your `Team.Hosting.*` packages there. Matching integrations appear in discovery and the `aspire add` picker. The built-in source remains enabled unless you set `integrationSources.default.enabled` to `false`.

#### Custom skills

Configure your team's agent plugins through `skillSources` in `aspire.config.json`. For example, point GitHub Copilot or Claude Code at your team's marketplace and select its plugin:

```json title="aspire.config.json — Configure a team plugin"
{
  "skillSources": {
    "team": {
      "repository": "example-org/team-skills",
      "marketplace": "team-skills",
      "plugins": ["platform"]
    }
  }
}
```

Replace the repository, marketplace, and plugin names with your own. Run `aspire agent init --skills aspire` from your project to apply the enabled sources to your selected agents. OpenCode uses skill catalog URLs instead of marketplace plugins.

<LearnMore>

#### Init source mechanism

Offer a shared starting configuration to everyone creating or initializing an app. Set **`ASPIRE_INIT_SOURCE_URL`** to a Git repository containing an `aspire.config.json` file:

```bash title="Aspire CLI — Offer a shared initialization source"
ASPIRE_INIT_SOURCE_URL=https://github.com/example-org/aspire-init.git \
  aspire init
```

Replace the URL with your configuration repository. The variable proposes a source; it doesn't silently apply it. The CLI displays the source and asks for consent. Use `--use-config-source` to accept explicitly or `--use-config-source false` to decline, including in non-interactive runs.

After acceptance, Aspire copies the source's `integrationSources` and `skillSources` into the project's local configuration and records its source binding. During template discovery, an explicitly configured URL can also supply `templateSources` without copying them into the project file. These are optional defaults, not enforced organizational policy.

Use `ASPIRE_INIT_SOURCE_PATH` to select a different configuration file within the repository, or `ASPIRE_INIT_SOURCE_REF` to select a branch or pin a full commit SHA. If you don't set a URL, the CLI normally offers no source, although detected internal Microsoft environments can supply an organizational default. Refresh an adopted configuration with `aspire update --config-source`.

Keep an eye on every running AppHost without repeatedly running `aspire ps`. The tray companion adds an Aspire icon to the macOS menu bar, the Windows notification area, or a Linux StatusNotifierItem tray, with a shared panel for your local AppHosts:

### More CLI improvements

- **WSLc container runtime**: Set `ASPIRE_CONTAINER_RUNTIME=wslc` on Windows to run, publish, and deploy containers with WSLc. `aspire doctor` checks only the configured runtime and reports features WSLc doesn't support.
- **Container tunnel base image**: Use a mirrored or customized tunnel image with `aspire config set containerTunnel.baseImage <image>`.

## 🐹 Go AppHost support

<span id="go-apphost-docs"></span>

Go AppHosts are generally available. You no longer need the `experimentalPolyglotGo` feature flag: create a Go AppHost with `aspire new`, using the `aspire-go-empty` or `aspire-go-starter` template, or add one to an existing app:

```bash title="Aspire CLI — Initialize a Go AppHost"
aspire init --language go
```

The starter template includes a Go API, a React frontend, and Redis. Go AppHosts also get first-class tooling:

- **Debugging**: Launch and debug `apphost.go` in VS Code through the Go extension's Delve adapter, and attach the debugger to running Go and .NET resources from the Aspire view.
- **Environment checks**: `aspire doctor` verifies that Go 1.26 or later is installed.
- **SDK and API reference**: Export the generated Go SDK's API with `aspire sdk export --language go`, and search Go API reference content with `aspire docs api search <query> --language go`.
- **Certificates**: On macOS and Windows, Go resources trust development certificates through the system certificate store by default.

The generated Go SDK uses idiomatic option structs and propagates child resource errors through `Build`.

Throughout aspire.dev, the landing page, AppHost builder, and hosting integration articles show `apphost.go` samples next to their C# and TypeScript equivalents. The AppHost language selection stays in sync across the page.

<LearnMore>
  See [Get started with the Go AppHost](/app-host/go-apphost/) and [Go
  AppHost conventions](/app-host/go-apphost-conventions/) for option structs,
  pointer helpers, and error handling.
</LearnMore>

## 🧩 AppHost updates

Aspire 17.0 raises its minimum supported .NET version to **.NET 10**. Review your AppHost and Aspire package target frameworks before updating. This requirement doesn't mean every workload orchestrated by Aspire must target .NET 10. For details, see [microsoft/aspire#20614](https://github.com/microsoft/aspire/pull/20614).

The `Aspire.Hosting.Dotnet` integration now follows stable package versioning for .NET projects added by path. The older `AddProject` APIs are deprecated, not removed. Use the path-based project model when updating your AppHost; see [microsoft/aspire#21360](https://github.com/microsoft/aspire/pull/21360) for migration details.

### Optional parameters

Not every parameter needs a value in every environment. Mark a parameter as optional, and Aspire stops prompting for it during `aspire run` and no longer fails publishing when it's unset. An unset optional parameter resolves to `null`, so consumers can fall back to their own defaults.

<Tabs syncKey='aspire-lang'>
  <TabItem label='TypeScript'>

```typescript title="apphost.ts"
const messagePrefix = await builder.addParameter('message-prefix').asOptional();
```

  </TabItem>
  <TabItem label='C#'>

```csharp title="AppHost.cs"
var messagePrefix = builder.AddParameter("message-prefix")
                           .AsOptional();
```

  </TabItem>
</Tabs>

Call `AsRequired` to make a parameter required again. In code, `ParameterResource.TryGetCurrentValue` reads a value without prompting, and `SetValueAsync` sets or clears one. The legacy manifest publisher doesn't support optional parameters. See [microsoft/aspire#18108](https://github.com/microsoft/aspire/pull/18108).

<LearnMore>
  See [External parameters](/fundamentals/external-parameters/) for optional
  parameter behavior during run and publish.
</LearnMore>

### Browser origins for CORS and redirects

Endpoints expose `PrimaryBrowserOrigin` and `BrowserOrigins`, deferred values that resolve to the origins a browser actually uses for a resource. They account for `*.dev.localhost` hosts, custom public URLs, and GitHub Codespaces forwarding, so CORS policies and authentication redirects keep working without hard-coded URLs:

```csharp title="AppHost.cs"
var frontendEndpoint = frontend.GetEndpoint("https");

backend.WithEnvironment("ALLOWED_ORIGINS", frontendEndpoint.BrowserOrigins)
       .WithEnvironment("FRONTEND_ORIGIN", frontendEndpoint.PrimaryBrowserOrigin);
```

When you deploy, Docker Compose, Kubernetes, and Radius publishers turn these values into deployment parameters. See [microsoft/aspire#21260](https://github.com/microsoft/aspire/pull/21260).

### TypeScript and JavaScript Azure Functions

`AddAzureFunctionsApp` hosts Azure Functions written in TypeScript or JavaScript. Functions apps can be published as the API for a static website with `PublishAsStaticWebsite`, and the Aspire VS Code extension can debug Node.js Functions. This API is experimental (`ASPIREAZUREFUNCTIONS001`).

```csharp title="AppHost.cs"
var functions = builder.AddAzureFunctionsApp(
    "functions", "../functions", AzureFunctionsLanguage.TypeScript);
```

See [microsoft/aspire#17980](https://github.com/microsoft/aspire/pull/17980) and [microsoft/aspire#20943](https://github.com/microsoft/aspire/pull/20943).

<LearnMore>

You can now author hosting integrations in TypeScript and consume them from polyglot AppHosts, starting with the preview `@aspire/nuxt` package. See [microsoft/aspire#16110](https://github.com/microsoft/aspire/pull/16110).

### APIs now stable

The following APIs no longer require you to suppress an experimental diagnostic:

- **File system and user secrets**: `ASPIREFILESYSTEM001` and `ASPIREUSERSECRETS001`.
- **Pipelines**: `ASPIREPIPELINES001`, `ASPIREPIPELINES002`, and `ASPIREPIPELINES004`.
- **Probes and commands**: `WithHttpProbe` (`ASPIREPROBES001`) and the `WithRequiredCommand` callback (`ASPIRECOMMAND001`).
- **Azure**: `ASPIREAZURE001` and Azure Container Apps naming (`ASPIREACANAMING001` and `ASPIREACANAMING002`).
- **Containers**: The Dockerfile builder (`ASPIREDOCKERFILEBUILDER001`) and compute endpoint mapping (`ASPIRECOMPUTE002`). Compute volume APIs remain experimental.
- **JavaScript and Deno**: `AddNextJsApp`, `PublishAsStaticWebsite`, `PublishAsNodeServer`, and `PublishAsPackageScript` (`ASPIREJAVASCRIPT001`), plus the Deno APIs (`ASPIREDENO001`).
- **Integrations**: `WithMcpServer` (`ASPIREMCP001`), connection string APIs (`ASPIRECONNECTIONSTRINGS001`), and the `Aspire.Hosting.Dotnet` package.

### More AppHost improvements

- **Resource traits (experimental)**: `WithTrait`, `WithTags`, and `WithDisplayOrder` attach metadata that tools and the dashboard can use (`ASPIRERESOURCETRAITS001`). See [microsoft/aspire#22206](https://github.com/microsoft/aspire/pull/22206).
- **Pipeline dependencies**: Custom pipeline steps can depend on deployment-target steps. See [microsoft/aspire#21511](https://github.com/microsoft/aspire/pull/21511).
- **Output diffing**: `WithOutputDiffing` is available through the standard usings. See [microsoft/aspire#21990](https://github.com/microsoft/aspire/pull/21990).
- **Idempotent bind mounts**: Repeating an identical `WithBindMount` call is a no-op, and a conflicting target throws. See [microsoft/aspire#21546](https://github.com/microsoft/aspire/pull/21546).
- **`*.localhost` in containers**: Container references to `*.localhost` hosts are remapped so they resolve inside the container. See [microsoft/aspire#21609](https://github.com/microsoft/aspire/pull/21609).
- **Interaction availability**: `IInteractionService.IsAvailable` returns `false` during `BeforeStart`, before the dashboard can show prompts. See [microsoft/aspire#21553](https://github.com/microsoft/aspire/pull/21553).

### `Aspire.AppHost.Sdk` is deprecated

C# AppHosts that use the `Aspire.AppHost.Sdk` MSBuild SDK now get warning `ASPIRE012`. The SDK remains available for staged migration. To migrate, switch the project's `Sdk` attribute to `Microsoft.NET.Sdk`, add `PackageReference` items for `Aspire.Hosting.AppHost` and `Aspire.Hosting.Dotnet`, and replace resource `ProjectReference` items with `AddDotnetProject` calls. To silence the warning temporarily, set `SuppressAspireAppHostSdkObsoleteWarning` to `true`. C# AppHosts also require the Aspire CLI bundle; see [ASPIRE013](/diagnostics/aspire013/). For details, see [microsoft/aspire#20867](https://github.com/microsoft/aspire/pull/20867).

## 🚀 Deployment updates

The `Aspire.Hosting.Kubernetes` and `Aspire.Hosting.Azure.Kubernetes` packages graduate to stable releases. Some APIs, including persistent-volume APIs, remain experimental. Helm-based deployment requires **Helm 4.0.0 or later**.

You can also target an existing Azure Kubernetes Service cluster rather than provisioning a new one. See [microsoft/aspire#20921](https://github.com/microsoft/aspire/pull/20921).

Azure Front Door can connect to Aspire-provisioned Azure Container Apps and App Service environments through Private Link. This API remains experimental, and the private endpoint connection must be approved before Front Door can reach the workloads. See [microsoft/aspire#21228](https://github.com/microsoft/aspire/pull/21228) and [microsoft/aspire#21396](https://github.com/microsoft/aspire/pull/21396).

### Azure Kubernetes Service

- **Standard tier by default**: New and updated AKS clusters use the Standard control-plane tier, which includes an uptime SLA and adds cost. See [microsoft/aspire#20917](https://github.com/microsoft/aspire/pull/20917).
- **Node pool OS SKU**: Choose a node OS, such as `AzureLinux`, with `AksNodePoolConfig.OsSku`. See [microsoft/aspire#21118](https://github.com/microsoft/aspire/pull/21118).
- **Separate identities**: Clusters use separate user-assigned identities for the control plane and kubelet, so images can be pulled from an existing registry in another resource group. See [microsoft/aspire#20919](https://github.com/microsoft/aspire/pull/20919).

### Kubernetes and cert-manager

- **External account binding**: Use ACME providers that require external account binding (EAB) by calling `WithExternalAccountBinding` after `WithAcmeServer`. The HMAC key must be a secret parameter, and it isn't written to published artifacts. See [microsoft/aspire#20918](https://github.com/microsoft/aspire/pull/20918).
- **File-based environment variables**: Generated manifests support Kubernetes `fileKeyRef` environment variable sources. See [microsoft/aspire#20847](https://github.com/microsoft/aspire/pull/20847).
- **Container registries in Helm charts**: Published charts honor the container registry configured for each image. See [microsoft/aspire#21121](https://github.com/microsoft/aspire/pull/21121).
- **Structured manifest fields**: Polyglot AppHosts can pass structured values to `withField` when customizing Kubernetes manifests. See [microsoft/aspire#22107](https://github.com/microsoft/aspire/pull/22107).

### More deployment improvements

- **Dashboard telemetry**: Dashboards in generated Docker Compose files and Helm charts opt out of dashboard usage telemetry with `ASPIRE_DASHBOARD_TELEMETRY_OPTOUT=true`. Your application's OpenTelemetry data isn't affected. See [microsoft/aspire#20906](https://github.com/microsoft/aspire/pull/20906).

### `ResourceUrlAnnotation.DisplayOrder` is now a property

`DisplayOrder` changed from an obsolete public field to a read/write property. Its behavior is unchanged: higher values display higher in the dashboard URL list.

Rebuild assemblies that access the field. Typical C# reads and assignments need no changes.

For details, see [microsoft/aspire#20637](https://github.com/microsoft/aspire/pull/20637).

### Legacy RabbitMQ and MongoDB client packages removed

Starting in Aspire 17.0, new releases no longer include `Aspire.RabbitMQ.Client.v6` or `Aspire.MongoDB.Driver.v2`. Previously published versions of these packages remain available on NuGet.

If your app references either legacy package, replace it with the corresponding current integration:

| Removed package             | Replacement package      | Client library version |
| --------------------------- | ------------------------ | ---------------------- |
| `Aspire.RabbitMQ.Client.v6` | `Aspire.RabbitMQ.Client` | `RabbitMQ.Client` 7.x  |
| `Aspire.MongoDB.Driver.v2`  | `Aspire.MongoDB.Driver`  | `MongoDB.Driver` 3.x   |

Update any direct client-library package references and migrate code that uses the older driver APIs. Follow the [RabbitMQ .NET Client 7.x migration guide](https://github.com/rabbitmq/rabbitmq-dotnet-client/blob/main/v7-MIGRATION.md) and the [MongoDB .NET/C# Driver 3.0 upgrade guide](https://www.mongodb.com/docs/drivers/csharp/v3.0/upgrade/v3/).

The service registration calls, `AddRabbitMQClient` and `AddMongoDBClient`, remain the same. This removal doesn't change the behavior of the current `Aspire.RabbitMQ.Client` and `Aspire.MongoDB.Driver` packages or the AppHost hosting integrations.

<LearnMore>
  See [Connect to RabbitMQ](/integrations/messaging/rabbitmq/rabbitmq-connect/)
  and [Connect to MongoDB](/integrations/databases/mongodb/mongodb-connect/) for
  current client setup guidance. For the removal details, see
  [microsoft/aspire#20608](https://github.com/microsoft/aspire/pull/20608).
</LearnMore>

### Azure Cosmos DB client options callback receives a service provider

The `configureClientOptions` parameter on the Azure Cosmos DB client integration now has the type `Action<IServiceProvider, CosmosClientOptions>` instead of `Action<CosmosClientOptions>`. This change applies to the client, container, and database registration methods, including their keyed variants.

Add an `IServiceProvider` parameter to each callback. You can use it to resolve services while configuring the client:

```csharp title="Program.cs"
builder.AddAzureCosmosClient(
    "cosmosdb",
    configureClientOptions: static (services, options) =>
    {
        options.ApplicationName = "myapp";
    });
```

The callback runs when the `CosmosClient` is first resolved from dependency injection, not during service registration. An exception in the callback therefore occurs when the client is resolved. Rebuild applications compiled against an earlier version: calls to these methods from older binaries throw `MissingMethodException`, even when they don't pass a callback.

For details, see [microsoft/aspire#19349](https://github.com/microsoft/aspire/pull/19349).

### Docker Swarm `MaxFailureRatio` now requires a number

The `MaxFailureRatio` property on Docker Swarm `UpdateConfig` changed from `string?` to `double?`. Docker Compose requires this value to be a number, so Aspire 17.0 publishes it without quotes.

Change string assignments to numeric assignments:

```diff title="UpdateConfig.cs"
- MaxFailureRatio = "0.3"
+ MaxFailureRatio = 0.3
```

For details, see [microsoft/aspire#21512](https://github.com/microsoft/aspire/pull/21512).


### `AddCSharpApp` is obsolete

`AddCSharpApp` now produces compiler warning CS0618. Add the `Aspire.Hosting.Dotnet` package and call `AddDotnetProject` (`addDotnetProject` in TypeScript), which returns a `DotnetProjectResource`:

```bash title="Aspire CLI"
aspire add Aspire.Hosting.Dotnet
```

```diff title="AppHost.cs"
- var api = builder.AddCSharpApp("api", "../Api");
+ var api = builder.AddDotnetProject("api", "../Api");
```

For details, see [microsoft/aspire#20825](https://github.com/microsoft/aspire/pull/20825).

### `Aspire.AppHost.Sdk` is obsolete

Projects that use `Aspire.AppHost.Sdk` get warning `ASPIRE012`. Follow the migration steps in [`Aspire.AppHost.Sdk` is deprecated](#aspireapphostsdk-is-deprecated), or temporarily set `SuppressAspireAppHostSdkObsoleteWarning` to `true`. For details, see [microsoft/aspire#20867](https://github.com/microsoft/aspire/pull/20867).

### `TerminalOptions.ShowTerminalHost` removed

Terminal host resources are always hidden from the dashboard, so the `ShowTerminalHost` option was removed. Delete any assignments to it. For details, see [microsoft/aspire#20756](https://github.com/microsoft/aspire/pull/20756).

### Polyglot feature keys renamed

The experimental polyglot feature flags no longer use a colon-separated suffix. Update `aspire.config.json` and any `aspire config set` scripts:

| Before                         | After                          |
| ------------------------------ | ------------------------------ |
| `experimentalPolyglot:java`    | `experimentalPolyglotJava`     |
| `experimentalPolyglot:go`      | `experimentalPolyglotGo`       |
| `experimentalPolyglot:python`  | `experimentalPolyglotPython`   |
| `experimentalPolyglot:rust`    | `experimentalPolyglotRust`     |

Go AppHosts no longer need a feature flag. For details, see [microsoft/aspire#20481](https://github.com/microsoft/aspire/pull/20481).

### Let's Encrypt cert-manager shortcuts removed

`WithLetsEncryptProduction` and `WithLetsEncryptStaging` were removed, along with the `WithAcmeServer` overload that mixed a literal server URL with a parameter email. Pass the ACME directory URL explicitly, using either two literals or two parameters:

```csharp title="AppHost.cs"
issuer.WithAcmeServer(
    "https://acme-v02.api.letsencrypt.org/directory",
    "admin@contoso.com");
```

For details, see [microsoft/aspire#20918](https://github.com/microsoft/aspire/pull/20918).

### AKS clusters use user-assigned identities

Aspire-provisioned AKS clusters now use separate user-assigned identities for the control plane and kubelet. When you redeploy an existing cluster, Azure may update its node pools, which can disrupt running workloads. Permissions you granted manually to the previous identities aren't transferred; grant them to the new identities. For details, see [microsoft/aspire#20919](https://github.com/microsoft/aspire/pull/20919).

### Polyglot `addNodePool` takes a callback

In polyglot AppHosts, `addNodePool` configures the pool through a callback instead of an options object. C# AppHosts are unchanged.

```typescript title="apphost.ts"
await aks.addNodePool('workers', async pool => {
  pool.minCount = 0;
});
```

Python AppHosts use camelCase keys for node pool settings. For details, see [microsoft/aspire#21118](https://github.com/microsoft/aspire/pull/21118).

### SQL Server REPL no longer discovers older `sqlcmd` paths

The SQL Server dashboard REPL now launches `/opt/mssql-tools18/bin/sqlcmd` directly. Images that only include the older `/opt/mssql-tools/bin/sqlcmd` client must select it explicitly:

```csharp title="AppHost.cs"
builder.AddSqlServer("sql")
       .WithRepl(options => options.Command = SqlServerReplCommand.Version17);
```

The default image and parameterless `WithRepl` call are unaffected. For details, see [microsoft/aspire#20704](https://github.com/microsoft/aspire/pull/20704).
