## 🆙 Upgrade to Aspire 17.0

<span id="upgrade-to-aspire-17"></span>
<br />

:::caution
Review the [Breaking changes](#breaking-changes) before upgrading.
:::

For general purpose upgrade guidance, see [Upgrade Aspire](/whats-new/upgrade-aspire/).

Once Aspire 17.0 is available on the stable channel, use the [`aspire update` command](/reference/cli/commands/aspire-update/):

<Steps>

1. Update the Aspire CLI itself:

   ```bash title="Aspire CLI — Update the CLI"
   aspire update --self
   ```

1. Update your projects from the repository root:

   ```bash title="Aspire CLI — Update all Aspire packages"
   aspire update
   ```

</Steps>

<LearnMore>
  For more details on installing the Aspire CLI, see [Install the
  CLI](/get-started/install-cli/).
</LearnMore>

## 🛠️ CLI updates

### Shell completion

Complete Aspire commands and options in Bash, Fish, PowerShell, and Zsh. Generate a completion script with `aspire completions script`, specifying `bash`, `fish`, `pwsh`, or `zsh` when you want to select the shell explicitly.

For example, generate and load a Bash completion script for your current shell session:

```bash title="Aspire CLI — Generate Bash completions"
aspire completions script bash > aspire-completion.bash
source ./aspire-completion.bash
```

For installation details, see [microsoft/aspire#20026](https://github.com/microsoft/aspire/pull/20026).

### Environment-specific secrets

Keep deployment secrets separate by using `--environment` or `-e` with the `aspire secret` commands.

Run the secret commands from your AppHost directory. You can set a secret without putting its value in the command line: omit the value to enter it at a masked interactive prompt, or use `--envvar` to read an environment variable:

```bash title="Aspire CLI — Set a deployment secret from an environment variable"
aspire secret set Parameters:database-password --environment production --envvar DATABASE_PASSWORD
```

Set `DATABASE_PASSWORD` in your environment before running this command. Non-interactive calls must supply a value or `--envvar`; they don't open an input prompt.

For details, see [microsoft/aspire#20135](https://github.com/microsoft/aspire/pull/20135) and [microsoft/aspire#20984](https://github.com/microsoft/aspire/pull/20984).

### Custom templates, integrations, and skills

Bring your team's project scaffolding, hosting packages, and agent guidance into the Aspire CLI. Named sources let you reuse these across apps without replacing Aspire's built-in choices. Use sources you trust: templates and agent plugins can contain executable code.

#### Custom templates

Try templates directly from a Git repository without registering a source. For example, browse the Azure-focused templates in [Azure/aspire-templates](https://github.com/Azure/aspire-templates):

```bash title="Aspire CLI — Try Azure templates"
aspire new --template-repository https://github.com/Azure/aspire-templates
```

Fork the repository and customize a template for your team. Push your changes to a branch, then use `--template-repository-ref` to test it before merging:

```bash title="Aspire CLI — Test a template branch"
aspire new --template-repository https://github.com/example-org/aspire-templates \
  --template-repository-ref custom-starter
```

Replace `example-org` with your fork's owner and `custom-starter` with your branch. The ref can also be a tag or full commit SHA; omitting it uses the repository's default branch. Use `--template-path` to select a directory within the repository.

When you want to reuse a source, add a persistent reference in your global Aspire settings:

```bash title="Aspire CLI — Save a template source"
aspire template source add azure --repository https://github.com/Azure/aspire-templates
aspire new
```

The CLI asks you to confirm that you trust the source before registering it. Use `--path` for a template directory within the repository and `--ref` to pin a branch, tag, or full commit SHA.

#### Custom integrations

Make your hosting integrations discoverable from a NuGet server. Add an `integrationSources` entry to `aspire.config.json`; optional package patterns limit which packages the source offers:

```json title="aspire.config.json — Discover team integrations"
{
  "integrationSources": {
    "team": {
      "source": "https://nuget.example.com/v3/index.json",
      "patterns": ["Team.Hosting.*"]
    }
  }
}
```

Replace the illustrative feed URL with your NuGet server's service index and publish your `Team.Hosting.*` packages there. Matching integrations appear in discovery and the `aspire add` picker. The built-in source remains enabled unless you set `integrationSources.default.enabled` to `false`.

#### Custom skills

Configure your team's agent plugins through `skillSources` in `aspire.config.json`. For example, point GitHub Copilot or Claude Code at your team's marketplace and select its plugin:

```json title="aspire.config.json — Configure a team plugin"
{
  "skillSources": {
    "team": {
      "repository": "example-org/team-skills",
      "marketplace": "team-skills",
      "plugins": ["platform"]
    }
  }
}
```

Replace the repository, marketplace, and plugin names with your own. Run `aspire agent init --skills aspire` from your project to apply the enabled sources to your selected agents. OpenCode uses skill catalog URLs instead of marketplace plugins.

<LearnMore>
  See [Configure AI agent plugins and skill sources](/reference/cli/configuration/#configure-ai-agent-plugins-and-skill-sources)
  for agent-specific settings, catalog URLs, and source defaults.
</LearnMore>

#### Init source mechanism

Offer a shared starting configuration to everyone creating or initializing an app. Set **`ASPIRE_INIT_SOURCE_URL`** to a Git repository containing an `aspire.config.json` file:

```bash title="Aspire CLI — Offer a shared initialization source"
ASPIRE_INIT_SOURCE_URL=https://github.com/example-org/aspire-init.git \
  aspire init
```

Replace the URL with your configuration repository. The variable proposes a source; it doesn't silently apply it. The CLI displays the source and asks for consent. Use `--use-config-source` to accept explicitly or `--use-config-source false` to decline, including in non-interactive runs.

After acceptance, Aspire copies the source's `integrationSources` and `skillSources` into the project's local configuration and records its source binding. During template discovery, an explicitly configured URL can also supply `templateSources` without copying them into the project file. These are optional defaults, not enforced organizational policy.

Use `ASPIRE_INIT_SOURCE_PATH` to select a different configuration file within the repository, or `ASPIRE_INIT_SOURCE_REF` to select a branch or pin a full commit SHA. If you don't set a URL, the CLI normally offers no source, although detected internal Microsoft environments can supply an organizational default. Refresh an adopted configuration with `aspire update --config-source`.

## 🧩 AppHost updates

Aspire 17.0 raises its minimum supported .NET version to **.NET 10**. Review your AppHost and Aspire package target frameworks before updating. This requirement doesn't mean every workload orchestrated by Aspire must target .NET 10. For details, see [microsoft/aspire#20614](https://github.com/microsoft/aspire/pull/20614).

The `Aspire.Hosting.Dotnet` integration now follows stable package versioning for .NET projects added by path. The older `AddProject` APIs are deprecated, not removed. Use the path-based project model when updating your AppHost; see [microsoft/aspire#21360](https://github.com/microsoft/aspire/pull/21360) for migration details.

<LearnMore>
  Follow the [17.0 project migration guide on GitHub](https://github.com/microsoft/aspire/blob/a509f094e0ee87d17dc0e1cc9bca84f7ca2623da/docs/migrate-from-addproject.md)
  for project paths, launch profiles, and scenarios that retain the legacy model.
</LearnMore>

## ✨ New integrations

### Microsoft Entra ID

Model application registrations alongside the services that use them with the new preview `Aspire.Hosting.Azure.EntraId` integration. You can provision registrations and service principals, or reference registrations you already manage.

References supply identity configuration to your workloads. They don't install authentication middleware or protect application routes; configure authentication and authorization in the consuming application.

Thanks to @jmprieur for the initial integration proposal in [microsoft/aspire#14668](https://github.com/microsoft/aspire/pull/14668).

<LearnMore>
  See the [Microsoft Entra ID integration](/integrations/security/microsoft-entra-id/)
  for registration, credential, and workload configuration.
</LearnMore>

### Azure API Management

Define an API gateway in your AppHost with the new preview `Aspire.Hosting.Azure.ApiManagement` integration. Model APIs, backends, and policies, and import OpenAPI documents from files or reachable deployed workload endpoints.

API Management is a deployment-only resource: it isn't provisioned during `aspire run`. Your local workloads can still run without an API Management service.

Thanks to @tommasodotNET for [microsoft/aspire#19664](https://github.com/microsoft/aspire/pull/19664).

<LearnMore>
  See [Azure API Management](/integrations/cloud/azure/azure-api-management/azure-api-management-get-started/)
  for setup and gateway configuration.
</LearnMore>

## 🐳 Default container image updates

<span id="dashboard-image-update"></span>

Generated Docker Compose and Kubernetes deployments now reference the published Aspire `17.0` dashboard image instead of the `13.6` image used by earlier 17.0 preview builds:

```yaml
# Before
image: "mcr.microsoft.com/aspire/nightly/dashboard:13.6"
```

```yaml
# After
image: "mcr.microsoft.com/aspire/nightly/dashboard:17.0"
```

Without an explicit override, publishers resolve the dashboard tag from the Aspire product version, so this applies automatically when you publish with Aspire 17.0. This doesn't change the dashboard image repository or switch generated deployments to the `latest` tag.

## ⚠️ Breaking changes

<span id="breaking-changes"></span>

| Change                                                                                              | Migration                                                                                              |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `ResourceUrlAnnotation.DisplayOrder` changed from a field to a property                             | Rebuild assemblies that use the field.                                                                 |
| Legacy `Aspire.RabbitMQ.Client.v6` and `Aspire.MongoDB.Driver.v2` packages removed                  | Switch to `Aspire.RabbitMQ.Client` and `Aspire.MongoDB.Driver`, and migrate to the 7.x and 3.x client libraries. |
| Azure Cosmos DB `configureClientOptions` now receives `IServiceProvider`                            | Add the service-provider parameter to callbacks and rebuild binaries that call these methods.          |
| Docker Swarm `UpdateConfig.MaxFailureRatio` changed from `string?` to `double?`                    | Assign a number such as `0.3` instead of a string such as `"0.3"`.                                     |

### `ResourceUrlAnnotation.DisplayOrder` is now a property

`DisplayOrder` changed from an obsolete public field to a read/write property. Its behavior is unchanged: higher values display higher in the dashboard URL list.

Rebuild assemblies that access the field. Typical C# reads and assignments need no changes.

For details, see [microsoft/aspire#20637](https://github.com/microsoft/aspire/pull/20637).

### Legacy RabbitMQ and MongoDB client packages removed

Starting in Aspire 17.0, new releases no longer include `Aspire.RabbitMQ.Client.v6` or `Aspire.MongoDB.Driver.v2`. Previously published versions of these packages remain available on NuGet.

If your app references either legacy package, replace it with the corresponding current integration:

| Removed package             | Replacement package      | Client library version |
| --------------------------- | ------------------------ | ---------------------- |
| `Aspire.RabbitMQ.Client.v6` | `Aspire.RabbitMQ.Client` | `RabbitMQ.Client` 7.x  |
| `Aspire.MongoDB.Driver.v2`  | `Aspire.MongoDB.Driver`  | `MongoDB.Driver` 3.x   |

Update any direct client-library package references and migrate code that uses the older driver APIs. Follow the [RabbitMQ .NET Client 7.x migration guide](https://github.com/rabbitmq/rabbitmq-dotnet-client/blob/main/v7-MIGRATION.md) and the [MongoDB .NET/C# Driver 3.0 upgrade guide](https://www.mongodb.com/docs/drivers/csharp/v3.0/upgrade/v3/).

The service registration calls, `AddRabbitMQClient` and `AddMongoDBClient`, remain the same. This removal doesn't change the behavior of the current `Aspire.RabbitMQ.Client` and `Aspire.MongoDB.Driver` packages or the AppHost hosting integrations.

<LearnMore>
  See [Connect to RabbitMQ](/integrations/messaging/rabbitmq/rabbitmq-connect/)
  and [Connect to MongoDB](/integrations/databases/mongodb/mongodb-connect/) for
  current client setup guidance. For the removal details, see
  [microsoft/aspire#20608](https://github.com/microsoft/aspire/pull/20608).
</LearnMore>
### Azure Cosmos DB client options callback receives a service provider

The `configureClientOptions` parameter on the Azure Cosmos DB client integration now has the type `Action<IServiceProvider, CosmosClientOptions>` instead of `Action<CosmosClientOptions>`. This change applies to the client, container, and database registration methods, including their keyed variants.

Add an `IServiceProvider` parameter to each callback. You can use it to resolve services while configuring the client:

```csharp title="Program.cs"
builder.AddAzureCosmosClient(
    "cosmosdb",
    configureClientOptions: static (services, options) =>
    {
        options.ApplicationName = "myapp";
    });
```

The callback runs when the `CosmosClient` is first resolved from dependency injection, not during service registration. An exception in the callback therefore occurs when the client is resolved. Rebuild applications compiled against an earlier version: calls to these methods from older binaries throw `MissingMethodException`, even when they don't pass a callback.

For details, see [microsoft/aspire#19349](https://github.com/microsoft/aspire/pull/19349).

### Docker Swarm `MaxFailureRatio` now requires a number

The `MaxFailureRatio` property on Docker Swarm `UpdateConfig` changed from `string?` to `double?`. Docker Compose requires this value to be a number, so Aspire 17.0 publishes it without quotes.

Change string assignments to numeric assignments:

```diff title="UpdateConfig.cs"
- MaxFailureRatio = "0.3"
+ MaxFailureRatio = 0.3
```

For details, see [microsoft/aspire#21512](https://github.com/microsoft/aspire/pull/21512).
