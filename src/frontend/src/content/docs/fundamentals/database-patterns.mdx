Most Aspire solutions include at least one database. During development you create that database, fill it with sample data, change its schema as your app evolves, and decide whether its data should survive a restart. When you deploy, you decide where the database runs and how schema changes reach it. This article describes the options Aspire gives you for each of these tasks, with examples you can adapt for your own solution.

The examples on this page use PostgreSQL but the same patterns apply to other database integrations such as SQL Server, MySQL, and MongoDB. Where an example needs an Object-Relational Mapper (ORM), it uses Entity Framework Core (EF Core) for .NET apps or Drizzle for JavaScript and TypeScript apps. In this article, a _script_ is any program that works with the database. It can be a SQL file, a shell script, or a program written in a language such as JavaScript or Python.

## Create a database

A database server, such as a PostgreSQL container, can host many databases. Your app needs a specific database on that server before it can create tables or store data. You can create that database from the AppHost, from your app's code, or by hand in the dashboard.

### Create a database in the AppHost

The simplest way to create a database is to add a database resource to the server resource in your AppHost. The PostgreSQL resources in the examples on this page come from the [📦 Aspire.Hosting.PostgreSQL](https://www.nuget.org/packages/Aspire.Hosting.PostgreSQL) package. Call <ApiReference name="Aspire.Hosting.PostgresBuilderExtensions.AddDatabase" /> on the server resource, then reference the database from the app that uses it:

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

const postgres = await builder.addPostgres('postgres');
const catalogdb = await postgres.addDatabase('catalogdb');

await builder.addNodeApp('api', './api', 'src/index.ts')
    .withReference(catalogdb)
    .waitFor(catalogdb);

await builder.build().run();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var builder = DistributedApplication.CreateBuilder(args);

var postgres = builder.AddPostgres("postgres");
var catalogdb = postgres.AddDatabase("catalogdb");

builder.AddDotnetProject("api", "../Api/Api.csproj")
    .WithReference(catalogdb)
    .WaitFor(catalogdb);

builder.Build().Run();
```

</TabItem>
</Tabs>

When the server resource is ready, Aspire creates the database if it doesn't already exist. <ApiReference name="Aspire.Hosting.ResourceBuilderExtensions.WithReference" /> passes the database's connection information to the app, and <ApiReference name="Aspire.Hosting.ResourceBuilderExtensions.WaitFor" /> makes sure the app doesn't start until the database is available.

To control how the database is created, for example to set a collation or an owner, replace the default creation script by using <ApiReference name="Aspire.Hosting.PostgresBuilderExtensions.WithCreationScript" />. SQL Server and MySQL support the same method.

<LearnMore>
  For more information, see [Add PostgreSQL resource with database scripts](/integrations/databases/postgres/postgres-host/#add-postgresql-resource-with-database-scripts). For details on how Aspire waits for the server to be ready, see [AppHost eventing APIs](/app-host/eventing/).
</LearnMore>

### Create a database in an orchestrated app

Sometimes the app needs to create its own database. For example, the app might connect to an existing server that isn't modeled in your AppHost, or it might create one database for each tenant. In this case, reference the server resource instead of a database resource, so the app receives a connection to the server.

<Pivot id="efcore">

EF Core can create the database for you. When an app applies migrations, EF Core creates the database first if it doesn't exist. `EnsureCreatedAsync` also creates the database, but it bypasses migrations, so use it only for prototypes and tests.

When a .NET app references a PostgreSQL server resource named `postgres`, Aspire passes a connection string to the server, without a database name. Add the database name to the connection string when you register the `DbContext`, then apply migrations when the app starts. This example assumes a `DbContext` named `CatalogContext`:

```csharp title="Program.cs"
using Microsoft.EntityFrameworkCore;
using Npgsql;

var builder = WebApplication.CreateBuilder(args);

builder.AddNpgsqlDbContext<CatalogContext>("postgres", configureSettings: settings =>
{
    settings.ConnectionString = new NpgsqlConnectionStringBuilder(settings.ConnectionString)
    {
        Database = "catalogdb"
    }.ConnectionString;
});

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    using var scope = app.Services.CreateScope();
    var context = scope.ServiceProvider.GetRequiredService<CatalogContext>();

    // Creates catalogdb if it doesn't exist, then applies pending migrations.
    await context.Database.MigrateAsync();
}

app.Run();
```

</Pivot>

<Pivot id="drizzle">

Drizzle doesn't create databases. Instead, connect to the server and run a `CREATE DATABASE` statement before you run migrations. When a JavaScript app references a PostgreSQL server resource named `postgres`, Aspire passes the server's connection URI in the `POSTGRES_URI` environment variable:

```typescript title="src/create-database.ts"
import pg from 'pg';

const client = new pg.Client({ connectionString: process.env.POSTGRES_URI });
await client.connect();

const { rowCount } = await client.query(
    'SELECT 1 FROM pg_database WHERE datname = $1', ['catalogdb']);

if (rowCount === 0) {
    await client.query('CREATE DATABASE catalogdb');
}

await client.end();
```

You can run this code when the app starts, or from a custom command that you trigger from the dashboard. The [Seed a database on startup or using a custom command](#seed-a-database-on-startup-or-using-a-custom-command) section shows both approaches.

</Pivot>

<LearnMore>
  For the environment variables that Aspire passes to apps for each resource, see [Connect to PostgreSQL](/integrations/databases/postgres/postgres-connect/).
</LearnMore>

### Create a database in a dashboard REPL terminal

To create a database by hand, open the database's own command-line client in the dashboard. Call <ApiReference name="Aspire.Hosting.PostgresBuilderExtensions.WithRepl" /> on the server resource to add a **REPL** command. The command opens `psql` in the dashboard's terminal dock, already signed in with the resource's credentials:

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

await builder.addPostgres('postgres').withRepl();

await builder.build().run();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var builder = DistributedApplication.CreateBuilder(args);

builder.AddPostgres("postgres").WithRepl();

builder.Build().Run();
```

</TabItem>
</Tabs>

Run the app, then in the Aspire dashboard, select the **REPL** command on the `postgres` resource, and enter the statement:

```sql title="psql"
CREATE DATABASE catalogdb;
```

The SQL Server, MySQL, MongoDB, and Redis integrations also provide REPL commands. A database that you create by hand is lost when its container is removed, unless you [persist the database](#persist-a-database-across-restarts).

:::caution
The REPL uses the resource's credentials and can modify or delete any data. Enable it only for trusted dashboard users.
:::

## Seed a database with sample data

Seeding fills a database with data before you use it, such as a product catalog or a set of test customers. Seed data lets you develop and test features against realistic content. Because database containers start empty by default, automate seeding so that every run starts from a known state.

### Seed a database in an orchestrated app

When your app seeds the database, the seed logic lives in source control next to the model it depends on. You can run it every time the app starts, run it on demand, or include it in your migrations.

#### Seed a database on startup or using a custom command

To seed on startup, run the seed code after the app connects to the database and before it handles requests. Make the code idempotent: check whether the data already exists before you insert it, so a restart doesn't add duplicate rows.

<Pivot id="efcore">

Configure seeding with the `UseSeeding` and `UseAsyncSeeding` options when you register the `DbContext`. EF Core runs this code when the database is created or migrated. Implement both options with the same logic, because the EF Core tools call the synchronous `UseSeeding` option. The following example seeds a product only when it doesn't exist, and registers the seed code only in development:

```csharp title="Program.cs"
using Microsoft.EntityFrameworkCore;

var builder = WebApplication.CreateBuilder(args);

builder.AddNpgsqlDbContext<CatalogContext>("catalogdb", configureDbContextOptions: options =>
{
    if (!builder.Environment.IsDevelopment())
    {
        return;
    }

    options.UseSeeding((context, _) =>
    {
        var products = context.Set<Product>();
        if (!products.Any(p => p.Name == "Sample product"))
        {
            products.Add(new Product { Name = "Sample product", Price = 9.99m });
            context.SaveChanges();
        }
    });

    options.UseAsyncSeeding(async (context, _, cancellationToken) =>
    {
        var products = context.Set<Product>();
        if (!await products.AnyAsync(p => p.Name == "Sample product", cancellationToken))
        {
            products.Add(new Product { Name = "Sample product", Price = 9.99m });
            await context.SaveChangesAsync(cancellationToken);
        }
    });
});

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    using var scope = app.Services.CreateScope();
    var context = scope.ServiceProvider.GetRequiredService<CatalogContext>();

    // Applies pending migrations, then runs the UseAsyncSeeding code.
    await context.Database.MigrateAsync();
}

app.Run();
```

To register the `DbContext` for SQL Server or MySQL instead, see [Seed data using EF Core](/integrations/databases/efcore/seed-database/#seed-data-using-ef-core).

</Pivot>

<Pivot id="drizzle">

The `drizzle-seed` package generates realistic random data from your schema. The following example seeds the `products` table only when it's empty:

```typescript title="src/seed.ts"
import { drizzle } from 'drizzle-orm/node-postgres';
import { seed } from 'drizzle-seed';
import { products } from './schema.ts';

export async function seedDatabase() {
    const db = drizzle(process.env.CATALOGDB_URI!);

    const existing = await db.select().from(products).limit(1);
    if (existing.length === 0) {
        await seed(db, { products }, { count: 50 });
    }
}
```

Call `seedDatabase()` when the app starts. Aspire passes the `CATALOGDB_URI` environment variable because the app references a database resource named `catalogdb`.

</Pivot>

To seed only when you choose, expose the seed code as an endpoint in your app, then add a custom HTTP command to the app resource. The command appears in the dashboard, and selecting it sends a request to the endpoint.

<Pivot id="efcore">

The endpoint adds the rows through the database context. It checks for existing rows first, so you can run the command more than once:

```csharp title="Program.cs"
using Microsoft.EntityFrameworkCore;

// After you build the app...

if (app.Environment.IsDevelopment())
{
    app.MapPost("/admin/seed", async (CatalogContext context) =>
    {
        if (!await context.Products.AnyAsync())
        {
            context.Products.Add(new Product { Name = "Sample product", Price = 9.99m });
            await context.SaveChangesAsync();
        }

        return Results.Ok(new { status = "Database seeded" });
    });
}
```

Add the command to the app resource with <ApiReference name="Aspire.Hosting.ResourceBuilderExtensions.WithHttpCommand" />:

#### Seed a database using ORM migrations

You can also include seed data in your migrations. The data is then applied in order with your schema changes, and it reaches every environment that runs the migrations. Use this approach for reference data that your app needs, such as a list of countries or order statuses, rather than for large sets of test data.

<Pivot id="efcore">

Call `HasData` in `OnModelCreating` to define seed rows as part of your model. Each row needs a primary key value:

```csharp title="CatalogContext.cs"
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<OrderStatus>().HasData(
        new OrderStatus { Id = 1, Name = "Pending" },
        new OrderStatus { Id = 2, Name = "Shipped" },
        new OrderStatus { Id = 3, Name = "Delivered" });
}
```

Then add a migration:

```bash title="Terminal"
dotnet ef migrations add SeedOrderStatuses
```

EF Core generates the insert, update, and delete statements needed to keep the rows in sync with the model. For more information, see [Model managed data](https://learn.microsoft.com/ef/core/modeling/data-seeding#model-managed-data) in the EF Core documentation.

</Pivot>

<Pivot id="drizzle">

Generate an empty custom migration:

```bash title="Terminal"
npx drizzle-kit generate --custom --name=seed-order-statuses
```

Drizzle Kit creates a SQL file in your migrations folder. Add your `INSERT` statements to that file:

```sql title="api/drizzle/0001_seed-order-statuses.sql"
INSERT INTO order_statuses (id, name) VALUES
    (1, 'Pending'),
    (2, 'Shipped'),
    (3, 'Delivered');
```

Drizzle applies the file in order with your other migrations. Drizzle Kit sets the number prefix in the file name. For more information, see [Custom migrations](https://orm.drizzle.team/docs/kit-custom-migrations) in the Drizzle documentation.

</Pivot>

To learn how to apply migrations when your app runs, see [Modify a database schema](#modify-a-database-schema).

### Seed a database in a dashboard REPL terminal

To add data by hand, open the database's REPL from the dashboard as described in [Create a database in a dashboard REPL terminal](#create-a-database-in-a-dashboard-repl-terminal), then paste your `INSERT` statements. Use the REPL to try out data or to fix a single row. For seed data that you need every time, save it as a script so you can repeat the process.

To run a SQL script automatically when the database container initializes, mount a folder of scripts into the container with <ApiReference name="Aspire.Hosting.PostgresBuilderExtensions.WithInitFiles" />:

```typescript title="apphost.mts"

const postgres = await builder.addPostgres('postgres');
await postgres.withInitFiles('./postgres-init');

await builder.build().run();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"

builder.AddPostgres("postgres")
    .WithInitFiles("./postgres-init");

builder.Build().Run();
```

</TabItem>
</Tabs>

PostgreSQL runs the _.sql_ and _.sh_ files in the folder in alphabetical order, against the default `postgres` database. The scripts run before Aspire creates the databases in your AppHost, so a script that seeds `catalogdb` creates that database and connects to it first:

```sql title="postgres-init/01-catalog.sql"
CREATE DATABASE catalogdb;
\c catalogdb

CREATE TABLE IF NOT EXISTS products
(
    id SERIAL PRIMARY KEY,
    name TEXT UNIQUE NOT NULL,
    price NUMERIC(10, 2) NOT NULL
);

INSERT INTO products (name, price)
VALUES
    ('Hiking boots', 89.99),
    ('Water bottle', 12.50),
    ('Trail map', 4.99)
ON CONFLICT DO NOTHING;
```

When Aspire later creates `catalogdb`, it finds the database and leaves it in place. An initialization script that creates tables can conflict with ORM migrations that create the same tables. Use initialization scripts for databases that your app doesn't manage with migrations.

PostgreSQL runs these scripts only when it initializes an empty data directory. If you [persist the database](#persist-a-database-across-restarts) with a data volume, the scripts don't run again until you remove the volume.

To run a separate seed program, add it to the AppHost as a resource that you start from the dashboard. Call <ApiReference name="Aspire.Hosting.ResourceBuilderExtensions.WithExplicitStart" /> so that the resource doesn't run with the rest of the app. The resource receives the database's connection information from `WithReference`, in the same way as the app.

<Pivot id="efcore">

## Modify a database schema

As your app evolves, its tables and columns change. Most teams manage these changes with migrations: versioned files, kept in source control, that each describe one change to the schema. An ORM tracks which migrations a database has already applied, so it applies only the new ones. Your ORM generates migrations from changes to your model.

<Pivot id="efcore">

Run `dotnet ef migrations add <name>` to generate a C# migration from changes to your `DbContext` model. For more information, see [Create migrations](/integrations/databases/efcore/migrations/#create-migrations).

</Pivot>

<Pivot id="drizzle">

Run `npx drizzle-kit generate` to generate a SQL migration from changes to your schema file. For more information, see [Migrations with Drizzle](https://orm.drizzle.team/docs/migrations) in the Drizzle documentation.

</Pivot>

### Apply schema migrations on startup

To keep the database schema in step with your code, apply pending migrations every time the app runs.

<Pivot id="efcore">

Add a migration resource to your AppHost with <ApiReference name="Aspire.Hosting.EFResourceBuilderExtensions.AddEFMigrations" /> from the [📦 Aspire.Hosting.EntityFrameworkCore](https://www.nuget.org/packages/Aspire.Hosting.EntityFrameworkCore) package. This package is in preview. Call <ApiReference name="Aspire.Hosting.EFMigrationResourceBuilderExtensions.RunDatabaseUpdateOnStart" /> to apply migrations when the AppHost starts, and make the app wait for the migrations to finish with <ApiReference name="Aspire.Hosting.ResourceBuilderExtensions.WaitForCompletion" />:

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();
```

The worker applies the migrations inside an execution strategy, so EF Core retries them after a transient connection error. It then stops the app:

```csharp title="MigrationService/Worker.cs"
using Microsoft.EntityFrameworkCore;

public class Worker(
    IServiceProvider serviceProvider,
    IHostApplicationLifetime lifetime) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var scope = serviceProvider.CreateScope();
        var context = scope.ServiceProvider.GetRequiredService<CatalogContext>();

        var strategy = context.Database.CreateExecutionStrategy();
        await strategy.ExecuteAsync(() => context.Database.MigrateAsync(stoppingToken));

        lifetime.StopApplication();
    }
}
```

### Modify a schema with a custom command

Applying migrations on every run isn't always what you want. For example, you might want to review a migration before you apply it, or apply it to a database that already holds data you care about. In these cases, apply the migrations on demand from a command in the dashboard.

You can also expose migrations as an endpoint in your app and call it with a custom HTTP command. Anyone who can reach the endpoint can change your schema, so the dashboard's confirmation prompt isn't enough protection on its own. Register the endpoint only in development, and require a shared secret that only the AppHost knows. For more information, see [Considerations when registering HTTP commands](/fundamentals/http-commands/#considerations-when-registering-http-commands).

The endpoint calls `MigrateAsync` on the database context. This example assumes that the app registers a `DbContext` named `CatalogContext`. For more information, see [Use Aspire to create an EF Core context](/integrations/databases/efcore/overview/#use-aspire-to-create-an-ef-core-context).

```csharp title="Program.cs"
using Microsoft.AspNetCore.Mvc;

// After you build the app...

if (app.Environment.IsDevelopment())
{
    app.MapPost("/admin/migrate", async (
        [FromHeader(Name = "X-Migration-Key")] string? key,
        IConfiguration config,
        CatalogContext context) =>
    {
        if (config["MIGRATION_KEY"] is not { Length: > 0 } expected || key != expected)
        {
            return Results.Unauthorized();
        }

        await context.Database.MigrateAsync();
        return Results.Ok(new { status = "Migrations applied" });
    });
}
```

You can also change a schema by hand. ## Persist a database across restarts

By default, Aspire removes a database container when the AppHost stops, so the database and its data are lost. To keep the data between runs, store it outside the container:

- Call <ApiReference name="Aspire.Hosting.PostgresBuilderExtensions.WithDataVolume" /> to store the data in a volume that the container runtime manages. Use a volume in most cases.
- Call <ApiReference name="Aspire.Hosting.PostgresBuilderExtensions.WithDataBindMount" /> to store the data in a folder on your machine. Use a bind mount when you need to open the data files directly.

To also keep the container itself running between runs, call <ApiReference name="Aspire.Hosting.ResourceBuilderExtensions.WithPersistentLifetime" />. A persistent container makes the AppHost start faster, but it doesn't protect your data on its own. If the container is recreated, for example after a configuration change, its data is lost unless it's stored in a volume. For databases, use a data volume and a persistent lifetime together:

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

const postgres = await builder.addPostgres('postgres');
await postgres.withDataVolume();
await postgres.withPersistentLifetime();

const catalogdb = await postgres.addDatabase('catalogdb');

await builder.build().run();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"

    .WithDataVolume()
```

When the data persists, plan how seed logic and initialization scripts behave on later runs. Initialization scripts run only against an empty data directory, and seed code should check for existing rows. Aspire generates the password on first run and stores it in the AppHost's user secrets. Set it yourself if you want to control or share it.

## Deploy a database with an Aspire solution

When you deploy, the database resources in your AppHost become part of the deployment. You choose between two models:

- Deploy the database as a container next to your app. The deployment target, such as Docker Compose, Kubernetes, or Azure Container Apps, runs the same database image that you use in development. Without a volume, the container starts with a new, empty database each time it's replaced, so attach a volume to keep the data between deployments.
- Use a managed database service, such as Azure Database for PostgreSQL or Azure SQL Database. The cloud provider stores the data, so it stays in place across deployments. Aspire creates the databases in your AppHost during the first deployment and doesn't recreate or delete them later.

To use a managed service when you deploy and a local container during development, call `RunAsContainer` on the Azure resource. This example uses the [📦 Aspire.Hosting.Azure.PostgreSQL](https://www.nuget.org/packages/Aspire.Hosting.Azure.PostgreSQL) package:

<Pivot id="efcore">

`RunDatabaseUpdateOnStart` affects only local runs. To apply migrations in a deployed environment, publish them as a container image with <ApiReference name="Aspire.Hosting.EFMigrationResourceBuilderExtensions.PublishAsMigrationBundle" />. The bundle is deployed with your app and applies pending migrations when it runs. If you want to review the SQL before it runs, call <ApiReference name="Aspire.Hosting.EFMigrationResourceBuilderExtensions.PublishAsMigrationScript" /> instead. It generates an idempotent SQL script during `aspire publish`, which you then run against the database yourself.

A migration bundle container exits after it applies the migrations. Configure each deployment target so that it doesn't restart the container:

- On Azure Container Apps, publish the migration resource as a job with <ApiReference name="Aspire.Hosting.ContainerAppExtensions.PublishAsAzureContainerAppJob" />. A manually triggered job doesn't run until you start it. To start it during deployment, see [Ensure successful migrations deployment](#ensure-successful-migrations-deployment).
- On Docker Compose, set the service's restart policy to `no` with <ApiReference name="Aspire.Hosting.DockerComposeServiceExtensions.PublishAsDockerComposeService" />, as shown in the following example.
- On Kubernetes, customize the generated manifest to use a `Job` workload, or set `restartPolicy: OnFailure`.

```typescript title="apphost.mts"
await migrations.withReference(catalogdb);
await migrations.waitFor(catalogdb);
await migrations.publishAsMigrationBundle({ publishContainer: true });
await migrations.publishAsDockerComposeService(async (resource, service) => {
    await service.restart.set('no');
```

- On Azure Container Apps, publish the migration resource as a job with <ApiReference name="Aspire.Hosting.ContainerAppExtensions.PublishAsAzureContainerAppJob" />. - On Docker Compose, set the service's restart policy to `no` with <ApiReference name="Aspire.Hosting.DockerComposeServiceExtensions.PublishAsDockerComposeService" />, as shown in the following example.
- On Kubernetes, customize the generated manifest to use a `Job` workload, or set `restartPolicy: OnFailure`.

### Ensure successful migrations deployment

When you deploy a new version of your app, the new code often expects the new schema. If the app starts before the migrations finish, or if the migrations fail, the app can fail at runtime. To prevent this, make the deployment apply migrations first, and stop it when they fail. Choose one of these approaches:

<Pivot id="efcore">

- [Add a custom step to the Aspire deployment pipeline](#run-migrations-in-the-deployment-pipeline) so that `aspire deploy` runs a migration job and waits for it to succeed before it updates the app.
- [Run an EF Core migration bundle in your CI/CD pipeline](#run-migrations-as-a-cicd-pre-deployment-step) before you call `aspire deploy`.

</Pivot>

<Pivot id="drizzle">

- [Add a custom step to the Aspire deployment pipeline](#run-migrations-in-the-deployment-pipeline) so that `aspire deploy` runs a migration job and waits for it to succeed before it updates the app.
- [Run `drizzle-kit migrate` in your CI/CD pipeline](#run-migrations-as-a-cicd-pre-deployment-step) before you call `aspire deploy`.

</Pivot>

Either way, the app version that's still running keeps serving requests while the migrations run. Write migrations that the old version of the app can tolerate. For example, add a column in one release and remove the old column in a later release.

#### Run migrations in the deployment pipeline

The `aspire deploy` command runs a pipeline of named steps, such as `provision-api-containerapp` and `deploy-api`. You can add your own steps to this pipeline and declare which steps must run before and after them. To make the app deployment wait for the migrations, deploy the migrations as a job and add a step that:

1. Runs after the step that creates or updates the migration job.
1. Starts the job and waits for it to finish. If the job fails, the step throws an error, and the pipeline stops.
1. Runs before the step that updates the app, so that the app is updated only after the migrations succeed.

The following examples deploy to Azure Container Apps, so they need the [📦 Aspire.Hosting.Azure.AppContainers](https://www.nuget.org/packages/Aspire.Hosting.Azure.AppContainers) package. Aspire creates or updates each container app or job in a step named `provision-<resource-name>-containerapp`. A manually triggered job doesn't run when it's deployed, so the custom step starts it with the `az containerapp job start` command and polls its status. To find the step names for your deployment target, run `aspire do diagnostics`, which prints the dependency graph of the pipeline.

Aspire creates the Azure deployment steps while it resolves the pipeline, after your AppHost code adds its own steps. If you name an Azure step in the `dependsOn` or `requiredBy` options of a new step, the pipeline fails with an `unknown step` error. Instead, add the step without dependencies, then add the dependencies in a pipeline configuration callback. Aspire runs this callback after all the steps exist. The callback also runs during pipeline passes that don't create the Azure steps, so it adds the dependencies only when it finds them.

<Pivot id="efcore">

Publish the migration bundle as a container image and deploy it as a manually triggered job with <ApiReference name="Aspire.Hosting.ContainerAppExtensions.PublishAsAzureContainerAppJob" />. Then add the custom step and the configuration callback. In C#, use `builder.Pipeline.AddStep` and `builder.Pipeline.AddPipelineConfiguration`. In TypeScript, use `pipeline.addStep` and `pipeline.configure`:

```typescript title="apphost.mts"
import { execFile } from 'node:child_process';
import { setTimeout as delay } from 'node:timers/promises';
import { promisify } from 'node:util';
import { createBuilder } from './.aspire/modules/aspire.mjs';

const run = promisify(execFile);

const builder = await createBuilder();

await builder.addAzureContainerAppEnvironment('env');

const postgres = await builder.addPostgres('postgres');
const catalogdb = await postgres.addDatabase('catalogdb');

const api = await builder.addDotnetProject('api', '../Api/Api.csproj');
await api.withReference(catalogdb);

// Deploy the migration bundle as a manually triggered job.
const migrations = await api.addEFMigrations('api-migrations');
await migrations.withReference(catalogdb);
await migrations.waitFor(catalogdb);
await migrations.publishAsMigrationBundle({ publishContainer: true });
await migrations.publishAsAzureContainerAppJob();

if (await builder.executionContext().isPublishMode()) {
    const pipeline = await builder.pipeline();

    await pipeline.addStep('run-api-migrations', async (context) => {
        const logger = await context.logger();
        const resourceGroup = process.env.Azure__ResourceGroup!;
        const job = ['--name', 'api-migrations', '--resource-group', resourceGroup];

        const { stdout } = await run('az', [
            'containerapp', 'job', 'start', ...job,
            '--query', 'name', '--output', 'tsv',
        ]);
        const execution = stdout.trim();
        await logger.logInformation(`Started migration job execution ${execution}.`);

        while (true) {
            await delay(10_000);
            const { stdout: output } = await run('az', [
                'containerapp', 'job', 'execution', 'show', ...job,
                '--job-execution-name', execution,
                '--query', 'properties.status', '--output', 'tsv',
            ]);
            const status = output.trim();

            if (status === 'Succeeded') {
                await logger.logInformation('Migrations applied.');
                return;
            }

            if (['Failed', 'Stopped', 'Degraded'].includes(status)) {
                throw new Error(`Migration job execution ${execution} ended with status ${status}.`);
            }
        }
    });

    // Azure creates its deployment steps while the pipeline resolves,
    // so add the dependencies in a configuration callback.
    await pipeline.configure(async (context) => {
        const steps = new Map();
        for (const step of await (await context.pipeline()).steps()) {
            steps.set(await step.name(), step);
        }

        const deployApp = steps.get('provision-api-containerapp');
        if (steps.has('provision-api-migrations-containerapp') && deployApp) {
            // Run after the migration job is created or updated,
            await steps.get('run-api-migrations').dependsOn('provision-api-migrations-containerapp');
            // and before the app is updated.
            await deployApp.dependsOn('run-api-migrations');
        }
    });
}

await builder.build().run();
```

```csharp title="AppHost.cs"
static async Task<string> RunAzAsync(string[] args, CancellationToken cancellationToken)
{
    var startInfo = new ProcessStartInfo("az") { RedirectStandardOutput = true };
    foreach (var arg in args)
    {
        startInfo.ArgumentList.Add(arg);
    }

    using var process = Process.Start(startInfo)!;
    var output = await process.StandardOutput.ReadToEndAsync(cancellationToken);
    await process.WaitForExitAsync(cancellationToken);

    if (process.ExitCode != 0)
    {
        throw new InvalidOperationException($"'az {string.Join(' ', args)}' failed.");
    }

    return output.Trim();
}
```

#### Run migrations as a CI/CD pre-deployment step

To apply migrations before the app is deployed, run them from your CI/CD pipeline before you call `aspire deploy`. If they fail, the pipeline stops before the deployment starts.

<Pivot id="efcore">

An EF Core migration bundle is a single executable that applies your migrations to a database. It doesn't need the .NET SDK or your source code, so you can run it from a CI/CD pipeline before you deploy.

To generate the bundle, publish the migration resource as a migration bundle. Set the target runtime to match your CI/CD agent, and make the bundle self-contained so that the agent doesn't need the .NET runtime:

A pipeline step named `<resource-name>-generate-migration-bundle` generates the bundle and writes it to the _efmigrations_ folder in the publish output. In your CI/CD pipeline, run that step on its own, run the bundle against the production database, and then deploy:

```bash title="Terminal"
# Generate the bundle at ./artifacts/efmigrations/api-migrations.
aspire do api-migrations-generate-migration-bundle --output-path ./artifacts

# Apply pending migrations. The command fails if any migration fails.
./artifacts/efmigrations/api-migrations --connection "$CATALOGDB_CONNECTION_STRING"

# Deploy the app only after the migrations succeed.
aspire deploy
```

Store the connection string in your CI/CD system's secret store, and make sure the agent can reach the database through its firewall. The step that generates the bundle doesn't deploy anything. You can run it in a build stage and pass the bundle to a later deployment stage as an artifact.

<LearnMore>
  For more information, see [Migration bundles](https://learn.microsoft.com/ef/core/managing-schemas/migrations/applying#bundles) in the EF Core documentation and the [`aspire do` command](/reference/cli/commands/aspire-do/).
