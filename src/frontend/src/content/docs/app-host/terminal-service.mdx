import { Tabs, TabItem } from '@astrojs/starlight/components';

For supported databases and caches, use `WithRepl()` to open a client in the dashboard without writing a custom command. For other interactive tools, create and manage a terminal with `TerminalService`.

Use `Aspire.Hosting.ApplicationModel.TerminalService` to launch an interactive process from your AppHost, display it in the dashboard, and automate its input. For example, a [resource command](/fundamentals/custom-resource-commands/) can open a persistent local shell or run `docker exec` against a container.

These are **AppHost-owned terminals**: the AppHost launches and owns the terminal workload. They differ from [resource terminals](/dashboard/terminals/), where Aspire runs the resource and a terminal exposes that resource's existing process.

:::caution[Experimental API]
The low-level terminal authoring APIs are experimental and [emit diagnostic `ASPIRETERMINAL001`](/diagnostics/aspireterminal001/). Their examples explicitly acknowledge it with `#pragma warning disable ASPIRETERMINAL001`. The integration-level `WithRepl()` methods don't require this suppression.
:::

:::note[AppHost language support]
The integration methods `withRepl()` and resource method `withTerminal()` are available to TypeScript AppHosts. Creating and automating AppHost-owned terminals directly with `TerminalService`, and displaying them with `PromptTerminalAsync`, aren't currently exported to TypeScript. The C#-only examples below apply to those lower-level operations.
:::

## Open a database or cache REPL

A read-eval-print loop (REPL) accepts commands and displays their results interactively. `WithRepl()` adds an opt-in **REPL** resource command that opens the integration's bundled client in the dashboard terminal dock. It doesn't replace the database server's process or require `WithTerminal()`.

Use the [matching staging CLI and AppHost packages](/dashboard/terminals/#try-the-staging-build) and a running Docker or Podman runtime. Add the hosting integration to your AppHost; for Redis:

```bash title="Add the Redis hosting integration"
aspire add Aspire.Hosting.Redis
```

Replace your AppHost code with the following example. For a file-based C# AppHost, retain its generated SDK and package directives.

<Tabs syncKey='aspire-lang'>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();
await builder.addRedis('cache').withRepl();

await builder.build().run();
```

</TabItem>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var builder = DistributedApplication.CreateBuilder(args);

builder.AddRedis("cache").WithRepl();

builder.Build().Run();
```

</TabItem>
</Tabs>

Run `aspire run`, wait for `cache` to be running, and select **REPL** from its resource commands in the dashboard. Type `PING` and press Enter; the authenticated client replies with `PONG`. Type `quit` and press Enter before closing the terminal tab.

The command is disabled until the container is running and its runtime ID is available. Each invocation creates a new dock terminal and uses the current container ID, including after a container restart. Reopen the REPL after restarting its container; an old session doesn't reconnect automatically.

### Supported clients

Call `WithRepl()` / `withRepl()` on the server or cache resource, not on the logical database returned by `AddDatabase` / `addDatabase`.

| Integration | Resource creation (C# / TypeScript) | Client and initial connection | Exit command |
| --- | --- | --- | --- |
| [PostgreSQL](/integrations/databases/postgres/postgres-host/) | `AddPostgres` / `addPostgres` | `psql`, configured credentials, `postgres` database. Use `\connect` to switch databases. | `\q` |
| [Redis](/integrations/caching/redis/redis-host/) | `AddRedis` / `addRedis` | `redis-cli`, configured password when present. | `quit` |
| [Valkey](/integrations/caching/valkey/valkey-host/) | `AddValkey` / `addValkey` | `valkey-cli`, configured password when present. | `quit` |
| [MongoDB](/integrations/databases/mongodb/mongodb-host/) | `AddMongoDB` / `addMongoDB` | `mongosh`, authenticates against `admin` and connects directly to the server, including replica set members. | `exit` |
| [MySQL](/integrations/databases/mysql/mysql-host/) | `AddMySql` / `addMySql` | `mysql`, `root` with the configured password. | `quit` |
| [SQL Server](/integrations/databases/sql-server/sql-server-host/) | `AddSqlServer` / `addSqlServer` | `sqlcmd`, `sa` with the configured password, `master` database. End each SQL batch with `GO` on its own line. | `QUIT` |

The clients run inside their containers through the configured Docker or Podman runtime; you don't need to install database clients on the AppHost machine. Custom container images must include the appropriate client. SQL Server supports `/opt/mssql-tools18/bin/sqlcmd` and the older `/opt/mssql-tools/bin/sqlcmd`.

Redis uses the in-container non-TLS loopback port when TLS is enabled. MongoDB uses the configured trust bundle when TLS is enabled; custom certificates must cover `localhost`. SQL Server trusts the local server certificate for this development session.

:::caution[Privileged access and cleanup]
REPL access is disabled by default and is only added in run mode, not publish mode. Enable it only for trusted dashboard users: clients use the configured credentials and aren't read-only. SQL Server sessions run as `sa`. Sharing the dashboard through a tunnel or remote development environment also exposes this capability to users who can execute resource commands.

Exit the database client before closing its tab. Closing a dock tab disposes the AppHost-owned runtime command, but the container runtime can leave the client process running inside the container. Stopping the container ends any remaining REPL processes. Passwords are passed through environment variables rather than command-line arguments, but terminal output and query history can still contain sensitive data.
:::

Use `WithTerminal()` for a resource whose main process is itself interactive. Use `WithRepl()` for an additional database or cache client in the dock. The REPL dock session isn't a resource-terminal target for [`aspire terminal tape play`](/reference/cli/commands/aspire-terminal-tape-play/).

## Resolve the service and configure a terminal

Resolve `TerminalService` from dependency injection, either through the built AppHost's `app.Services.GetRequiredService<TerminalService>()` or a callback's service provider, such as `commandContext.Services`. You don't construct or register the service yourself.

The terminal types are in `Aspire.Hosting.ApplicationModel`, which AppHost projects import automatically when implicit usings are enabled.

`CreateTerminal(new TerminalLaunchOptions { ... })` returns an `AspireTerminal` handle. Launch options are properties of `TerminalLaunchOptions` itself; you don't need a terminal-library builder or a separate process-options object.

| Option | Purpose |
| --- | --- |
| `Title` | Required, nonblank terminal title. |
| `Executable` | Required executable name or path. A name is resolved against `PATH`. |
| `Arguments` | An `IList<string>`, initially empty. Pass arguments individually rather than building a shell command line. |
| `WorkingDirectory` | Defaults to the AppHost's working directory when omitted. |
| `EnvironmentVariables` | Adds or overrides entries in the inherited AppHost environment; it doesn't replace the entire environment. |
| `Columns`, `Rows` | Initial grid size, defaulting to 80 × 24. Both must be positive. A dashboard viewer can resize the grid. |
| `Placement` | Fixed at creation. Defaults to `TerminalPlacement.Dock`. |

Choose the placement independently of the workload:

- **`Dock`**: A tab in the dashboard's terminal dock.
- **`Dialog`**: A caller-owned terminal that an interaction dialog can borrow. It isn't listed in the dock.
- **`None`**: A terminal used only by automation, with no dashboard presentation.

`TerminalPlacement.ResourceView` is reserved for resource-owned terminals. Passing it to `CreateTerminal` throws.

## Open a persistent local shell

This complete AppHost uses an Alpine container as the resource on which to display a custom command. Start the AppHost with Docker available, then select **Open local shell** on the `tools` resource in the dashboard. The shell runs on the **AppHost machine**, not inside the container.

```csharp title="AppHost.cs"
using Microsoft.Extensions.DependencyInjection;

#pragma warning disable ASPIRETERMINAL001

var builder = DistributedApplication.CreateBuilder(args);

builder.AddContainer("tools", "alpine", "3.22")
    .WithArgs("sleep", "infinity")
    .WithCommand("local-shell", "Open local shell", commandContext =>
    {
        var terminals = commandContext.Services
            .GetRequiredService<TerminalService>();

        // Keep the caller-owned terminal alive after this command returns.
        var terminal = terminals.CreateTerminal(new TerminalLaunchOptions
        {
            Title = "Local shell",
            Executable = OperatingSystem.IsWindows() ? "cmd.exe" : "/bin/sh",
            Arguments = OperatingSystem.IsWindows() ? [] : ["-i"],
            WorkingDirectory = builder.AppHostDirectory,
            Placement = TerminalPlacement.Dock
        });

        terminal.Start();
        terminal.Show();

        return Task.FromResult(CommandResults.Success());
    });

builder.Build().Run();
```

`Start()` is idempotent and nonblocking: it schedules the workload, but doesn't wait for output. Call it explicitly when you want the workload running before a viewer attaches. `Show()` reveals the dock and selects the terminal's tab in **every connected dashboard**, not just the browser that invoked the command. It doesn't make a dialog terminal visible.

Don't put this dock terminal in an `await using` declaration inside the command. That would dispose it as soon as the command returned. It remains available until you dispose it, the user closes its dock tab, or the AppHost shuts down.

## Open a container exec session

This variant launches the Docker CLI on the AppHost machine and opens a shell inside the container. It requires a running Docker container and the `docker` command on the AppHost's `PATH`. Use `-it` so Docker allocates an interactive TTY inside the container.

```csharp title="AppHost.cs"
using Microsoft.Extensions.DependencyInjection;

#pragma warning disable ASPIRETERMINAL001

var builder = DistributedApplication.CreateBuilder(args);
var containerName = $"aspire-terminal-tools-{Guid.NewGuid():N}";

builder.AddContainer("tools", "alpine", "3.22")
    .WithContainerName(containerName)
    .WithArgs("sleep", "infinity")
    .WithCommand("container-shell", "Open container shell", commandContext =>
    {
        var terminals = commandContext.Services
            .GetRequiredService<TerminalService>();

        var terminal = terminals.CreateTerminal(new TerminalLaunchOptions
        {
            Title = "Container shell",
            Executable = "docker",
            Arguments = ["exec", "-it", containerName, "/bin/sh"],
            Placement = TerminalPlacement.Dock
        });

        terminal.Start();
        terminal.Show();

        return Task.FromResult(CommandResults.Success());
    });

builder.Build().Run();
```

Wait until `tools` is running before invoking the command. `WithContainerName` supplies the actual Docker name: the Aspire resource name alone isn't a reliable `docker exec` target because generated container names can have suffixes. The unique name in this example also avoids collisions with other AppHosts.

The AppHost owns this terminal's local `docker exec` workload, not the container's main process. This isn't the same as enabling a terminal on the container resource.

For supported databases and caches, prefer [the built-in REPL command](#open-a-database-or-cache-repl): it resolves the configured runtime, current container ID, and client credentials for you. For custom exec sessions, exit the in-container program before closing its tab; disposing the local runtime command doesn't guarantee that the remote process stops.

## Automate without a viewer

The `AspireTerminal` handle exposes text and key input, bounded waits, and a snapshot of the current screen:

- `SendTextAsync(text, cancellationToken)` sends text as though typed.
- `SendKeyAsync(AspireTerminalKey.Enter, cancellationToken)` sends a keypress. Other keys include `Tab`, the arrows, and `Escape`. Compose modifiers with a key, for example `AspireTerminalKey.Ctrl(AspireTerminalKey.C)` for Ctrl+C.
- `WaitForTextAsync(text, timeout, cancellationToken)` waits for text on the current screen. The default timeout is 30 seconds; a timeout throws `TimeoutException`.
- `GetScreenText()` returns the current screen with newline-separated lines, not a process-exit result or a complete log archive.

The following helper runs on Linux or macOS with `/bin/sh`. Add the local function to your AppHost file after the top-level app setup, with the diagnostic suppression at the top. Call it from an asynchronous AppHost callback with the resolved service and the callback's cancellation token.

```csharp title="AppHost.cs — headless helper"
#pragma warning disable ASPIRETERMINAL001

static async Task<string> RunHeadlessAsync(
    TerminalService terminals, CancellationToken cancellationToken)
{
    await using var terminal = terminals.CreateTerminal(new TerminalLaunchOptions
    {
        Title = "Headless check",
        Executable = "/bin/sh",
        Arguments =
        [
            "-c",
            """
            printf 'Ready for input\n'
            read -r answer
            printf 'Received:%s\n' "$answer"
            read -r finish
            """
        ],
        Placement = TerminalPlacement.None
    });

    terminal.Start();
    await terminal.WaitForTextAsync(
        "Ready for input", TimeSpan.FromSeconds(10), cancellationToken);
    await terminal.SendTextAsync("hello", cancellationToken);
    await terminal.SendKeyAsync(AspireTerminalKey.Enter, cancellationToken);
    await terminal.WaitForTextAsync(
        "Received:hello", TimeSpan.FromSeconds(10), cancellationToken);

    return terminal.GetScreenText();
}
```

The script stays alive at its final `read` until the helper disposes the terminal. This matters: after an **AppHost-owned workload stops**, input and screen-automation operations throw `InvalidOperationException`. The terminal remains registered and visible until disposal, but reopening it shows its ended state rather than replaying output.

Use distinctive, complete replies when automating. Waiting for text that also appears in the terminal's echoed input can report success before the command actually runs. Polling loops should have deadlines and observe cancellation; don't wait indefinitely for a prompt that might never appear.

## Acquire a resource terminal handle

`TryGetTerminal(string terminalId, out AspireTerminal? terminal)` resolves both AppHost-owned and resource-owned terminals. Resource terminal IDs use `resource:<resource-name>:<replica-index>`, with a zero-based replica index.

For a running shell resource named `shell` configured with `WithTerminal()`, this local function acquires its first replica's handle and sends an Enter key. Add it to your AppHost file after the top-level app setup, with the diagnostic suppression at the top:

```csharp title="AppHost.cs — resource terminal helper"
#pragma warning disable ASPIRETERMINAL001

static async Task SendEnterAsync(
    TerminalService terminals, CancellationToken cancellationToken)
{
    if (!terminals.TryGetTerminal("resource:shell:0", out var terminal))
    {
        throw new InvalidOperationException("The shell terminal isn't registered.");
    }

    await using (terminal)
    {
        await terminal.SendKeyAsync(AspireTerminalKey.Enter, cancellationToken);
    }
}
```

A successful lookup establishes registration, not that the workload is ready to accept input. Automation shares the resource's live terminal with its viewers, so coordinate input rather than typing over someone else's work.

`Start()` is a no-op on resource-owned terminals: the resource starts its workload. Disposing this handle releases the automation connection, **not the resource or its terminal producer**. A later lookup can acquire a fresh handle.

## Separate terminal and dialog lifetimes

For short-lived modal workflows, create a `Dialog` terminal with `await using`, start it, and pass it to [`IInteractionService.PromptTerminalAsync`](/extensibility/interaction-service/#terminal-interactions). The interaction **borrows** the handle and never disposes it. You can reuse the same live terminal across multiple prompts before the owner disposes it.

Keep these lifetimes separate:

| Lifetime | What ends it |
| --- | --- |
| AppHost-owned workload | Its process exits, or terminal disposal stops it. |
| AppHost-owned terminal | Explicit disposal, dock-tab close for a dock terminal, or AppHost shutdown. |
| Terminal interaction | Successful work completion, explicit interaction completion, or cancellation—not process exit. |
| Resource-owned producer | Resource lifecycle, not disposal of an acquired automation handle. |
