Console applications and background workers can participate in an Aspire application regardless of the language they're written in. Add them to your AppHost to manage their lifecycle alongside your other resources, provide connection strings and service endpoints, and view their console output in the dashboard.

## Adding a console app to the AppHost

Choose the resource type that matches how your app runs. Use an executable resource for a command-line program, a Python app resource for a script or module, or a JavaScript app resource for a Node.js app. For a .NET console app or Worker Service project, use a project resource. None of these apps needs to expose an HTTP endpoint to be orchestrated by Aspire.

<LearnMore>
  For more information on executable, Python, and JavaScript resources, see
  [Executable resources](/app-host/executable-resources/), [Python
  integration](/integrations/frameworks/python/), and [JavaScript
  integration](/integrations/frameworks/javascript/).
</LearnMore>

The following examples show how to add a .NET console app and configure service discovery and background workers with the .NET Generic Host.

These examples assume an existing AppHost and a shared service defaults project. Create the named console, worker, and API projects before referencing them. In a C# AppHost, add project references so the corresponding `Projects.*` types are generated; in a TypeScript AppHost, use each project's actual path.

For the Redis examples, install the hosting integration in your AppHost. Running Redis also requires a supported [container runtime](/get-started/prerequisites/).

<InstallPackage packageName="Aspire.Hosting.Redis" />

<Tabs syncKey='aspire-lang'>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var builder = DistributedApplication.CreateBuilder(args);

var cache = builder.AddRedis("cache");

// Add a console app project to the AppHost
var processor = builder.AddProject<Projects.MyConsoleApp>("processor")
    .WithReference(cache);

builder.Build().Run();
```

</TabItem>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

const cache = await builder.addRedis('cache');

// Add a console app project to the AppHost
await builder
  .addProject('processor', '../MyConsoleApp/MyConsoleApp.csproj')
  .withReference(cache);

await builder.build().run();
```

</TabItem>
</Tabs>

The `processor` project receives the `ConnectionStrings__cache` environment variable at runtime, just like any other project type.

<Aside type="note">
  The console app project should target a .NET version supported by Aspire (.NET
  8 or later) and reference the service defaults project to benefit from
  telemetry and service discovery. For more information, see [Service
  defaults](/get-started/csharp-service-defaults/).
</Aside>

## Service discovery in console apps

Console apps using the .NET Generic Host can use the same service discovery infrastructure as web apps. The following walkthrough assumes a `MyConsoleApp` console project and a `CatalogService` API project that exposes an HTTP endpoint at `/`.

<Steps>

1.  From the console project directory, install the hosting package:

    <InstallDotNetPackage packageName="Microsoft.Extensions.Hosting" />

    Add a reference to your existing service defaults project in the console project's _MyConsoleApp.csproj_. Replace the example path with your project's actual path:

    ```xml title="MyConsoleApp.csproj"
    <ItemGroup>
      <ProjectReference Include="..\MyApp.ServiceDefaults\MyApp.ServiceDefaults.csproj" />
    </ItemGroup>
    ```

2.  Add a typed HTTP client to the console project:

    ```csharp title="CatalogClient.cs"
    using System.Net.Http;

    public sealed class CatalogClient(HttpClient httpClient)
    {
        public Task<string> GetAsync(CancellationToken cancellationToken = default)
            => httpClient.GetStringAsync("/", cancellationToken);
    }
    ```

3.  Configure the host in your console app's _Program.cs_. This example starts the host, calls the catalog API, and then stops:

    ```csharp title="Program.cs"
    using Microsoft.Extensions.DependencyInjection;
    using Microsoft.Extensions.Hosting;

    var builder = Host.CreateApplicationBuilder(args);

    // Add service defaults (telemetry, health checks, service discovery)
    builder.AddServiceDefaults();

    // Register your services
    builder.Services.AddHttpClient<CatalogClient>(
        client => client.BaseAddress = new Uri("https+http://catalog"));

    using var app = builder.Build();
    await app.StartAsync();

    var catalogClient = app.Services.GetRequiredService<CatalogClient>();
    Console.WriteLine(await catalogClient.GetAsync());

    await app.StopAsync();
    ```

4.  In the AppHost, reference the services this app depends on:

          <Tabs syncKey='aspire-lang'>

    <TabItem id='csharp' label='C#'>

    ```csharp title="AppHost.cs"
    var builder = DistributedApplication.CreateBuilder(args);

    var catalog = builder.AddProject<Projects.CatalogService>("catalog");

    var processor = builder.AddProject<Projects.MyConsoleApp>("processor")
        .WithReference(catalog)
        .WaitFor(catalog);

    builder.Build().Run();
    ```

          </TabItem>

    <TabItem id='typescript' label='TypeScript'>

    ```typescript title="apphost.mts"
    import { createBuilder } from './.aspire/modules/aspire.mjs';

    const builder = await createBuilder();

    const catalog = await builder.addProject(
      'catalog',
      '../CatalogService/CatalogService.csproj'
    );

    const processor = await builder.addProject(
      'processor',
      '../MyConsoleApp/MyConsoleApp.csproj'
    );
    await processor.withReference(catalog);
    await processor.waitFor(catalog);

    await builder.build().run();
    ```

          </TabItem>

    </Tabs>

</Steps>

The `WithReference(catalog)` call injects service discovery configuration so `processor` can resolve `https+http://catalog` to the running catalog service endpoint.

## Background worker services

Worker Service projects are the recommended pattern for long-running background tasks with Aspire. They use `IHostedService` (or `BackgroundService`) and integrate naturally with the .NET Generic Host.

### Creating a Worker Service

Create a `DataWorker` project with the Worker Service template, then add a reference to your shared service defaults project as shown in the console walkthrough:

```bash title=".NET CLI"
dotnet new worker --name DataWorker --output DataWorker
```

From the `DataWorker` directory, install the Redis **client** integration. This package supplies `AddRedisClient`; the AppHost's hosting package doesn't register a client in the worker:

<InstallDotNetPackage packageName="Aspire.StackExchange.Redis" />

Replace the generated worker class with _DataProcessor.cs_. Its `DoWorkAsync` method is a placeholder for your application's processing logic; registering the Redis client doesn't itself perform Redis operations.

```csharp title="DataProcessor.cs"
using Microsoft.Extensions.Hosting;
using Microsoft.Extensions.Logging;

public class DataProcessor : BackgroundService
{
    private readonly ILogger<DataProcessor> _logger;

    public DataProcessor(ILogger<DataProcessor> logger)
    {
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            _logger.LogInformation("Processing data at: {Time}", DateTimeOffset.UtcNow);

            await DoWorkAsync(stoppingToken);

            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
    }

    private Task DoWorkAsync(CancellationToken stoppingToken)
    {
        // Replace with your background work.
        return Task.CompletedTask;
    }
}
```

```csharp title="Program.cs"
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

var builder = Host.CreateApplicationBuilder(args);

builder.AddServiceDefaults();

// Register resource connections
builder.AddRedisClient("cache");

// Register the background worker
builder.Services.AddHostedService<DataProcessor>();

var app = builder.Build();
await app.RunAsync();
```

### Adding to the AppHost

The following model also provides a PostgreSQL database. Install its hosting integration in the AppHost before using this example:

<InstallPackage packageName="Aspire.Hosting.PostgreSQL" />

The database reference supplies connection information, but the worker above doesn't yet use it. To add database operations, configure a client as described in [Connect to PostgreSQL](/integrations/databases/postgres/postgres-connect/).

<Tabs syncKey='aspire-lang'>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var builder = DistributedApplication.CreateBuilder(args);

var cache = builder.AddRedis("cache");
var db = builder.AddPostgres("postgres").AddDatabase("app-db");

var worker = builder.AddProject<Projects.DataWorker>("data-worker")
    .WithReference(cache)
    .WithReference(db)
    .WaitFor(db);

builder.Build().Run();
```

</TabItem>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

const cache = await builder.addRedis('cache');
const postgres = await builder.addPostgres('postgres');
const db = await postgres.addDatabase('app-db');

const worker = await builder.addProject(
  'data-worker',
  '../DataWorker/DataWorker.csproj'
);
await worker.withReference(cache);
await worker.withReference(db);
await worker.waitFor(db);

await builder.build().run();
```

</TabItem>
</Tabs>

## Explicit start and console interaction

By default, all resources start automatically when the AppHost runs. For console apps that should only run on demand, use `WithExplicitStart`.

<Tabs syncKey='aspire-lang'>
<TabItem id='csharp' label='C#'>

```csharp title="AppHost.cs"
var builder = DistributedApplication.CreateBuilder(args);

var tool = builder.AddProject<Projects.MyInteractiveTool>("tool")
    .WithExplicitStart();

builder.Build().Run();
```

</TabItem>
<TabItem id='typescript' label='TypeScript'>

```typescript title="apphost.mts"
import { createBuilder } from './.aspire/modules/aspire.mjs';

const builder = await createBuilder();

const tool = await builder.addProject(
  'tool',
  '../MyInteractiveTool/MyInteractiveTool.csproj'
);
await tool.withExplicitStart();

await builder.build().run();
```

</TabItem>
</Tabs>

With `WithExplicitStart`, the resource appears in the Aspire dashboard but doesn't start automatically. You can start it manually from the dashboard or programmatically.

<Aside type="caution">
  Interactive console apps that read from stdin (for example,
  `Console.ReadLine()`) aren't fully supported in the Aspire dashboard's
  **Console logs** view. The dashboard captures and displays stdout/stderr, but
  the console logs page doesn't forward user input to the process's stdin.
</Aside>

Aspire builds that include the experimental `WithTerminal` API support interactive terminal user interfaces (TUIs) and shell-based experiences that need a live, bidirectional session, separately from the dashboard's console log viewer.

:::caution[Experimental API]
`WithTerminal` is reported under diagnostic ID `ASPIRETERMINAL001`. Using it in C# requires suppressing that diagnostic, and its API surface and behavior may change. This API might not be present in your installed release; use compatible hosting packages and a CLI build that includes it.
:::

## Viewing console output

Aspire captures stdout and stderr from all managed resources and displays them in the dashboard's **Console logs** page. Console apps output is fully visible, including colored text (ANSI escape codes are rendered).

<LearnMore>
  For more information, see [Console logs
  page](/dashboard/explore/#console-logs-page).
</LearnMore>

For structured logging in console apps, use `ILogger` instead of `Console.Write`. The following fragment assumes an existing logger and item identifier:

```csharp title="Program.cs"
// Prefer structured logging
logger.LogInformation("Processing item {ItemId}", itemId);

// Instead of
Console.WriteLine($"Processing item {itemId}");
```

With console logging and OpenTelemetry logging/export configured, such as through the service defaults setup above, logs appear in both the **Console logs** and **Structured logs** views of the dashboard. Calling `ILogger` alone doesn't export structured logs to the dashboard.

## Using connection strings without service defaults

If you can't use the service defaults project (for example, in a minimal console app without a host), you can access connection strings directly from environment variables:

For the configuration API example, install the environment variables configuration provider in your console project:

<InstallDotNetPackage packageName="Microsoft.Extensions.Configuration.EnvironmentVariables" />

```csharp title="Program.cs"
// For .NET apps, read from configuration
using Microsoft.Extensions.Configuration;

var config = new ConfigurationBuilder()
    .AddEnvironmentVariables()
    .Build();

var redisConnection = config.GetConnectionString("cache");
// Or equivalently:
var redisConnection2 = Environment.GetEnvironmentVariable("ConnectionStrings__cache");
```

<Aside type="tip">
  When using configuration APIs directly, use `GetConnectionString("cache")`
  rather than reading `ConnectionStrings__cache` directly. The configuration
  system maps the double-underscore separator to the colon used by
  `IConfiguration`, making `ConnectionStrings:cache` and
  `ConnectionStrings__cache` equivalent. For more information, see [Resource
  naming conventions](/app-host/resource-naming/).
</Aside>
